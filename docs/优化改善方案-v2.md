# 应用锁 v2 优化改善方案

> 基于 v0.3 → v1.10.6 全部迭代与当前代码扫描（2026-10-07）
> 诊断输入：20 个页面 / 19 个 core 模块 / 4 个前台服务 / watcher 837 行 / blocked.json 五类条目 / 两套并存的旧守护系统

---

## 一、现状诊断

### 1.1 功能臃肿与冲突（对应问题 ①）

**根因一：三层配置没有统一决策点。**
当前生效行为由 `AmsController.writeRules()` 手工合并五类条目：

| 层 | 粒度 | 存储 | 条目 |
|---|---|---|---|
| 界面锁定 | activity | LockRule (rules.json) | `c` + r(深链) + u(到期) |
| 每日限额 | package | LockRule.quotaMin → QuotaState | `p` |
| 到点跳转 | package | SessionCfg (sessions.json) | `f` + s/t/n/g/m |
| 专注会话 | package | FocusSession | `p` |
| 全局豁免 | 全局 | UnlockExemptions | `g` |

冲突处理散落在 writeRules 的 if 分支里（如 f 条目在超额/专注时静默跳过、quotaMin 同包取最大、verifyMode null=跟随全局），**用户在界面上看不到任何一层"最终生效的是什么"**。

**根因二：新旧两套守护系统并存。**
早期实现的 `AutoRelockService`（解锁后重新锁/宽限期，1353 行 UI）和 `AutoFreezeService`（退出后延迟冻结/锁屏即冻，839 行 UI）与新机制三重重叠：

- 退出后延迟冻结 ≈ 息屏清栈 + 到点跳转冷静期
- 解锁后重新锁 ≈ 解锁验证 + 到期解锁
- 各自还有独立的前台服务、独立磁贴（LockAllRelockTileService）、独立的 store

用户面对"自动锁闭 / 自动冻结 / 到点跳转 / 定时计划 / 时间范围 / 每日限额"六个名字相近的入口，不可能分清。

### 1.2 失效功能（对应问题 ②）

本轮迭代全程只验证了新功能路径，以下旧功能从未回归测试（嫌疑清单）：

- **AutoFreeze / AutoRelock**：与 watcher 的 blocked.json 存在双写冲突（LockEngine 与 AmsController 都写规则文件），互相覆盖风险高
- **桌面搜索直达**（ShortcutManagerCompat requestPinShortcut，v0.9）之后未测
- **临时解锁每日次数上限**（tempUnlockDailyMax，v1.2）之后未测
- **磁贴三件套**：v1.6 修了 PendingIntent 但只做了冒烟；LockAllRelock 与 LockAll 功能重叠
- **场景模式**（SceneEngine 启停 + 验证）与时间范围 enforceWindow 的交互
- **29 条预置深链**：随各 App 版本迭代大量过期（v0.9 修正过一次，之后 4 个大版本无校验）
- **息屏清栈** screen_off_kill 开关
- **到期解锁的 UI 入口**在 GridDetailDialog 无显示（设了也看不见）

**排查方案**：建立 `smoke_test.md` + adb 冒烟脚本（每功能一条可自动执行的验证命令/手势），一次性回归；长期挂在构建后执行。

### 1.3 搜索跳转的难点（对应问题 ③）

现状：跳转依赖逐 App 配置的深链（29 条预置 + 手填），只覆盖头部 App；深链随目标 App 更新失效后无降级；用户的核心诉求"点开抖音 → 到抖音里搜东西"对长尾 App 无法配置。

**方案：把"直跳搜索页"升级为"Reroute 过渡页"（统一拦截出口）**

watcher 拦截后不再静默直跳，而是拉起本 App 的 `RerouteActivity`（exported，intent 携带目标包名）：

```
┌──────────────────────────┐
│   打开「抖音」前，先喘口气  │  ← 圆环呼吸 5 秒（冲动消退曲线）
│                          │
│  [ 搜索关键词________ ]   │  ← 动态搜索
│  在抖音内搜索 | 浏览器搜索  │  ← 有深链用深链(xhsdiscover://search/result?keyword=xx)
│                           │     无深链自动降级浏览器 keyword 搜索
│  仍要打开（需过解锁验证）    │  ← 强度不减
└──────────────────────────┘
```

- 解决"针对搜索的 App"：关键词动态输入，深链库有则精确进站内搜索页，没有则通用浏览器兜底，**任何 App 都覆盖**
- 解决深链过期：拉起失败自动降级浏览器，用户无感
- 呼吸延迟是 one-sec 等产品验证过的有效机制（冲动 5-10 秒即消退）
- 过渡页同时承载拦截计数动画（正反馈）和"仍要打开"验证入口（自律强度不降）
- 旧"直跳搜索页"模式保留为设置项（老用户习惯不变）

### 1.4 名字、图标与布局（对应问题 ④）

**改名候选**（"应用锁"商店重名严重且只表达了 10% 的功能）：

| 候选 | 理由 | 风险 |
|---|---|---|
| **收心**（推荐） | 直指功能本质——收住玩心；两个字好记好念；情绪价值强 | 重名中 |
| 闸门 Gate | 系统级拦截的意象，英文好传播 | 偏硬 |
| 暂离 | 强调"暂"——不剥夺只延迟，符合产品哲学 | 搜索歧义 |

**图标**：保留"拱门+钥匙孔"基因（已有识别度），配合新名重绘一版更饱满的（当前线条稿在桌面上偏弱），monochrome 层同步。

**信息架构重组**（16 页 → 9 页）：

```
底部 4 Tab
├─ 总览   状态卡 + 当前生效规则总览（新增，解决"不知道怎么设置的"）+ 今日拦截
├─ 锁定   收藏夹宫格 + 应用列表（合并 2 页）；每 App 详情聚合其全部规则
├─ 用量   每日限额 + 到点跳转 + 统计守护（合并 3 页）
└─ 设置
    ├─ 守护时机：定时计划 + 时间范围 + 专注（合并 3 页）
    ├─ 验证体系：解锁验证 + 锁定强度（合并 2 页）
    ├─ 自动守护：AutoRelock/AutoFreeze 二合一或下线
    └─ 系统：Shizuku/磁贴/防卸载/方案库/历史/关于
```

核心新增：**「生效规则总览」**——按 App 列出所有层叠规则与最终行为（"抖音：限额 30 分/日 + 连刷 5 分跳微信读书 + 23:00-07:00 全锁 + 解锁需答题 3 道"），冲突一目了然。这是解决问题 ① 的钥匙。

### 1.5 我的补充意见（代码层，对应问题 ⑤）

1. **建立 EffectiveRules 决策引擎**（最重要）：把五层合并逻辑从 writeRules 的 if 分支提炼为纯 Kotlin 函数 `fun decide(rules, sessions, quota, focus, exempt): Map<pkg, Decision>`，watcher 消费它的输出，UI 总览页也消费它——单一真源，冲突可见、可单测。这是架构上解决"臃肿冲突"的根本。
2. **LockRule 拆分**：当前 LockRule 同时承载界面锁定/验证/限额/到期四类职责，是"界面-应用-全局"混乱的模型根源。拆为 LockRule（锁定+验证）与 AppPolicy（限额/会话等应用级），UI 与引擎随之清晰。
3. **下线或合并 AutoFreeze/AutoRelock**：两服务两屏 2200 行，功能被新机制覆盖 90%。建议 P0 直接下线（保留数据迁移），把"退出后延迟冻结"这一仍有价值的场景并入到点跳转的宽限逻辑。
4. **WatcherMain 拆模块**：837 行单文件塞了拦截/会话/统计/豁免/跳转五件事，拆成 Blocker/SessionTracker/Stats/Redirect 四个类，规则解析单测覆盖。
5. **blocked.json schema 版本化**：加 `"v":21` 字段，watcher 遇到不认识的版本忽略新字段而非整份失效，避免 App/Watcher 版本错配时全盘失灵。
6. **深链库数据化**：从 Kotlin 硬编码改为 assets JSON，加"上次验证时间"，过渡页检测失败自动降级并标记。
7. **磁贴精简**：四个磁贴（临时解锁/全部锁/全部解锁/重锁）→ 三个（临时解锁/一键全锁/状态），重锁磁贴并入自动守护。

## 二、路线图

### P0 止血与排查（1 轮，先做）
1. AutoFreeze/AutoRelock 下线开关（默认关，数据保留），消除双写冲突
2. 冒烟清单执行：嫌疑清单逐项真机验证，失效的当轮修复
3. 生效规则总览页 v1（先只读展示，不做编辑）
4. 磁贴精简

### P1 决策引擎 + 过渡页（1-2 轮）
1. EffectiveRules 引擎 + 单元测试
2. RerouteActivity 过渡页（搜索动态关键词 + 呼吸延迟 + 仍要打开验证）
3. 深链库降级机制

### P2 品牌 + 信息架构（2 轮）
1. 定名 + 图标重绘 + 全应用文案替换
2. 四 Tab 信息架构落地，16 页 → 9 页
3. 锁定弹窗/编辑弹窗按新模型简化（App 级策略聚合编辑）

### P3 打磨（持续）
1. WatcherMain 拆分 + blocked.json 版本化
2. LockRule → LockRule + AppPolicy 模型拆分
3. 冒烟脚本自动化挂到构建
