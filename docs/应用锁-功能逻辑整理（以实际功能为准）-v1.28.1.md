## 0. 一页看懂

| 能力 | 实现方式 | 关键数据 | 入口 |
|---|---|---|---|
| 锁一个界面 | 组件禁用 `pm disable-user`，失败降级为系统级启动拦截 | `rules.json` | 工作台 / 应用页 |
| 拦截后跳转深链 | 拦截模式下拒绝启动 + 拉起 `redirectUri` | `LockRule.redirectUri` | 条目编辑弹窗 |
| 自动锁回 | 前台服务三条链路（解锁后 / 退出后 / 锁屏后） | `relock.json` | 设置 → 自动锁闭 |
| 解锁要验证 | 等待 / 密码 / 答题 / 随机码；界面级 > 应用级 > 全局 | `unlock_verify` + `rules.json` | 设置 → 解锁验证 |
| 每日限额 | 每分钟统计使用时长，超额整包拦到额度提示页 | `LockRule.quotaMin` + `quota_state` | 设置 → 时长限额 |
| 专注会话 | 会话期间整包静默拦截目标 App | `focus_state.json` | 设置 → 专注会话 |
| 到点跳转 | 连续使用 N 分钟自动拉起学习 App | `sessions.json` | 条目编辑弹窗 |
| 场景 / 定时 | 一键套用一组方案 / 时间窗内强制上锁 | `scenes.json` / `schedules.json` | 工作台 / 设置 |
| 临时解锁 | 全局豁免一段时间（有每日次数上限） | `exempt_state` + `lock_strength` | 磁贴 |

**运行前提**：**Shizuku 已安装并授权**。本 App 无 root，所有系统级动作（禁用组件、拉起 shell 拦截进程、抓取前台、读统计文件）全部经 Shizuku 执行。Shizuku 掉线 = 拦截与统计全停。

## 1. 总体架构

### 1.1 五条并行的约束层

所有约束最终都归到**一份拦截清单**，由 `AmsController.writeRules()` 生成 `blocked.json`，交给 shell 身份的 Watcher 常驻进程读取。清单里条目形态不同，优先级也不同：

| 层 | JSON 字段 | 来源 | 语义 | 优先级 |
|---|---|---|---|---|
| 常驻规则 | `c` = 包/类 | `LockRule`（`block && locked`） | 锁这个界面 | 最低 |
| 到点跳转 | `f` = 包，`s`/`t`/`n`/`g`/`m` | `SessionCfg` | 连续用 N 秒后跳走 / 当日锁死 | 中 |
| 专注会话 | `f`（实际写 `p`）→ 见下 | `FocusState` | 会话期间整包拦 | 高 |
| 包级超额 | `p` = 包 | `QuotaState.overPackages()` | 额度用完，整包拦到提示页 | 最高 |
| 全局豁免 | `g=1`，`u` = 截止时间 | `UnlockExemptions` | 期间全部放行 | 单独判定 |

> 说明：专注会话与包级超额走的是**包级条目**（`p` 字段），Watcher 按包整包拒绝；到点跳转走**会话条目**（`f` 字段），由 Watcher 自己计时。超额包会被跳过专注层与跳转层（有更严的拦截，不需要软引导）。

### 1.2 双引擎（`LockEngine`）

```
lock(pkg, cls)
├─ 有跳转深链 → lockWithRedirect()      // 只能走拦截，组件必须保持启用
└─ 无跳转     → pm disable-user 四次尝试
                 ├─ 成功（且 isDisabled 为真）→ 完成
                 └─ 系统限制（HyperOS）→ lockByController()
```

- **pm 通道**：挨个试 `pm disable-user --user 0` / `pm disable-user` / `pm disable --user 0` / `pm disable`。判成功**不看返回码单独说了算**，还要 `AppStore.isDisabled()` 确认组件真的没了；成功后 `am force-stop` 清残留任务栈（否则点图标只是「恢复已有任务」，不产生启动请求，也就不可能被拦）。
- **拦截通道**：写 `block=true` → 下发规则 → `AmsController.ensureStarted()` 拉起 Watcher。失败时**回滚**（`removeRule` + 重写清单），不留「显示已锁、实际没锁」的脏条目。
- **为什么有跳转就必须走拦截**：`pm disable-user` 在包管理层生效，点图标连启动请求都不产生，`IActivityController` 根本感知不到，跳转无从谈起。

### 1.3 解锁

`LockEngine.unlock()`：先 `pm enable` 恢复组件（如果是 pm 模式），再把 `locked` 置 false（**条目保留**，白名单语义），重写清单，记历史，最后埋点 `AutoRelock.noteUnlocked()`。**解锁不删除收藏条目**。

### 2.1 `LockRule`（一个界面 = 一条）

| 字段 | 含义 |
|---|---|
| `packageName` / `activityName` | 目标组件 |
| `note` | 用户备注（列表标题优先用它，否则用类名末段） |
| `block` | `true` = 拦截模式；`false` = pm 组件禁用 |
| `locked` | 当前是否锁定 |
| `redirectUri` | 拦截后跳转的深链；`null`/空串 = 纯拦截 |
| `verifyMode` / `verifyDelaySec` / `verifyPassword` / `quizCount` | 界面级解锁条件；`null` = 跟随应用级 → 全局 |
| `quotaMin` | 每日限额（分钟），按**包**取最大值；`null` = 不限额 |
| `lockUntil` | 锁定有效期（epoch ms），到期 Watcher 自动放行 |

> `rules.json` 的写方法**全部 `@Synchronized`**：UI 主线程、`LockEngine` 的 IO 线程、广播线程都会写，不加锁会「刚锁的条目莫名丢了」，甚至把文件写坏。

### 2.2 `RelockData` / `ActivityRelockCfg`

```kotlin
RelockData(
  relockAfterUnlock, relockOnExit, relockOnScreenOff,   // 全局三条链路的开关
  globalDelaySec, globalExitDelaySec, globalScreenOffDelaySec,
  lastOnScenes,        // 总开关关闭时的快照
  activities,          // 界面级覆盖：List<ActivityRelockCfg>
  schema = 6,
)
ActivityRelockCfg(pkg, cls,
  unlockParticipate, unlockDelaySec,      // -1 = 跟随全局
  exitParticipate, exitDelaySec,
  screenOffParticipate, screenOffDelaySec)
```

默认值：解锁后 **5 分钟** / 退出后 **5 分钟** / 锁屏后 **立即**。`MAX_DELAY_SEC = 100_000_000`（只防 Int 溢出，不是业务上限）。

## 3. 锁定引擎细节

### 3.1 保存跳转的唯一入口 `LockEngine.saveRedirect()`

为什么不能只写字段：跳转只在「拦截模式 + 组件仍启用」下成立。旧实现只调 `AppStore.updateRedirect()`，对一条 pm 模式的条目补填跳转 = **静默无效**（界面显示已保存，点图标毫无反应）。

`saveRedirect()` 的做法：

1. 先写字段；
2. 判 `需要重锁 = 有跳转 && 已锁定 && (!block || 组件仍被禁用)`；
3. 不需要 → 只 `writeRules()`；需要 → 走一次 `apply(lock=true, redirect)` 把它切到拦截模式。

### 3.2 空串必须当 null

`effectiveRedirect()` 两处（入参、已存字段）都要把 `""` 过滤成 `null`。历史数据里存在 `redirectUri = ""`，原样返回会让一条纯拦截条目被误判为「有跳转」，下发 `r=""` 的规则。

### 3.3 锁定有效期

`lockUntil > 0` 时，`writeRules()` 会给该条目带上 `"u": lockUntil`，Watcher 过期后自动放行——不依赖 App 存活。到期后收藏条目仍保留，用户可手动再锁。

### 3.4 失败必须可见

`LockOutcome(locked, mode, detail)` 三个字段一路传回 UI：`mode = none` 时 toast「操作失败：{detail}」。自动锁闭链路里失败会同时 `Log.w` + 把常驻通知文案改成「有界面重锁失败，请检查 Shizuku 是否存活」。**不允许静默失败**——否则用户只看到「功能坏了，什么都没发生」。

### 3.5 跳转目标的三种格式（v1.28.0 新增第三种）

`WatcherMain.buildTargetIntent()` 按顺序判：

| 写法 | 判据 | 构造 | 适用 |
|---|---|---|---|
| **深链** | 含 `://` | `ACTION_VIEW` + data（无组件 → **隐式**） | 大多数 app 的搜索页 |
| **组件** | 含 `/` | `setComponent()`（**显式**） | 搜索是独立导出 Activity 时 |
| **`组件|uri`** ★ | 含 `\|` | 先 `setComponent()` 再 `setData()` | **同一 scheme 注册在多个组件上** |
| 裸类名 | 其它 | `ComponentName(pkg, target)` | 输入框里只填类名 |

**为什么需要第三种**：酷安把 `coolmarket://` 同时注册在 `MainActivity`（带 authority + path）和 `AppLinkActivity`（只声明 scheme、无任何限制）上 → 隐式 Intent **双匹配 → 弹系统选择器**。而纯组件 `.view.search.SuperSearchActivity` 虽然 WARM 能直达，**COLD 会漂回 `MainActivity` 停在首页信息流**。只有「显式 `MainActivity` + data」既躲开选择器、又能稳定落到搜索页。

输入框、`validateRedirectTarget()`、「测试跳转」、`startViaAm()`、`startViaBinder()` 五处都认这个格式（后两者复用 `buildTargetIntent()`）。

### 3.6 自我跳转豁免（`SELF_JUMP_UNTIL`，v1.28.0）

`activityStarting` 的规则匹配有一个前提：**只拦显式组件**——`cn == null` 的隐式深链直接放行（所以淘宝那种纯深链写法从来不撞这个坑）。而 `组件|uri` 的跳转目标 `MainActivity` **正是被拦的那个组件** → 不处理就会**自己拦自己**，或者被判 `BAD-TARGET` 抑制 60 秒。

做法：`maybeRedirect()` 里**先**把 `pkg` 记入 `SELF_JUMP_UNTIL`（`now + 3s`）**再**发 intent；`activityStarting` 看到该包在窗口内且**非桌面来源**就 `ALLOW(self-jump)`。

- 豁免是 **per-pkg**（只影响该包）、**3 秒**、**只放行 `!userLaunch`** —— 用户点桌面图标（`MAIN + LAUNCHER`）照拦。
- 自环判据只比 **uri 部分**（`target.indexOf('|')` 之后），因为组件每次都会被 `MainActivity` 原样透传回来，整体比对永不相等。
- 即刻这类「深链 → `RouteActivity` → 真实页」的**多跳链路**同样吃这个豁免。
- 已知取舍：窗口内该包所有非桌面启动都放行（不只是跳转目标）。窗口 3 秒、且需恰好在此期间从非桌面路径进入，风险可接受。

## 4. 自动锁闭（两层模型）

### 4.1 模型

- **作用域 = 收藏夹全部已锁定条目**。不再有「应用名单 / 界面名单」。
- **两层**：全局三开关 + 三延迟；界面级对每条链路有「参与否决」和「延迟覆盖」。
- `AutoRelockStore.NOT_LOCK = -1`：约定「不锁」。

### 4.2 裁决顺序（唯一入口 `AutoRelock.lockSec(pkg, cls, link)`）

```
1. 全局该链路开关关 → -1（总闸，一票否决，不受界面级影响）
2. cls != null 且该界面有配置，且该链路 participate = false → -1（界面级否决）
3. 延迟 = 界面级 delaySec >= 0 ? delaySec : 全局 delaySec
   ↑ 特例：exit 链路按包触发（cls = null）时，取该包内所有 exitDelaySec >= 0 的**最小值**
     （更早锁 = 更强，宁可早不可晚）
```

`lockedByState(pkg, cls, link) = lockSec(...) >= 0` —— **UI 上所有自动锁闭开关的显示值都必须走它**，不允许读原始配置字段（那会造出「亮着但不生效」的假开关）。

### 4.3 三条链路（`AutoRelockService`）

| 链路 | 触发 | 计时起点 | 到点动作 |
|---|---|---|---|
| 解锁后 | `AutoRelock.noteUnlocked()`（验证解锁成功） | 解锁时刻 | 该界面单独锁回 |
| 退出后 | 前台包名变化，且离开的包受管辖 | 离开前台的时刻 | **该包下全部**已解锁且仍参与「退出后」的条目一起锁回 |
| 锁屏后 | `ACTION_SCREEN_OFF` | 熄屏时刻 | 延迟 0 → 立刻锁；延迟 > 0 → 记入 `screenOffPending`，到点**仍是熄屏**才锁 |

服务实现要点：

- `scheduleWithFixedDelay(safeTick, 0, 1000ms)`，**不用 `postDelayed`**（不堆积任务）。
- 三张 pending 表（`pendingRelock` / `exitPending` / `screenOffPending`）全在单线程 executor 上读写；`screenOn` 是 `@Volatile`（广播在主线程写）。
- **去重节流 3 秒**：`mayLock(key)`。快速亮灭屏会让 `ACTION_SCREEN_OFF` 在 1~2 秒内连发，没有节流就是 N 次 Shizuku 子进程 + N 次写规则，还可能把刚解锁的界面再锁一次。
- **前台保护**（解锁后链路）：到点前**当场补查一次** `currentForeground()`。不能只依赖 `lastForeground`——它由「退出后」链路维护，只开「解锁后」的用户那里恒为空串，正在用的 App 会被到点锁掉。命中前台就放弃这次待锁并清 pending。
- **到点二次校验**：三条链路都是「先查 `isTracked(...)` 再锁」。等待期间用户关掉开关 → 放弃。缺这道校验就会出现「关了开关还会被锁回去」。
- **亮屏即放弃**：`ACTION_SCREEN_ON` 清空 `screenOffPending`（用户回来了，不需要锁了）。
- **不活跃就跳过**：`AutoRelock.active() = 任一开关开 && 收藏夹里有已锁定条目`；不成立时直接清表返回，零开销。

### 4.4 界面级覆盖的 UI 是场景行，不是「一个总开关」

`AutoRelockScreen`（设置 → 自动锁闭）**只放全局**：顶部说明卡 + 「启用自动锁闭」总开关 + 三张场景卡（开关 + 延迟，点延迟弹 `DurationField`）。

界面级在**工作台 → 宫格 → 某个界面的「自动锁闭」**（`FavoritesScreen` 的 `relockCfgRule` 弹窗）里配，也是三张场景行：

```
解锁后      跟随全局 ▸        [ ● ]
退出后      10 秒（蓝）▸      [ ● ]
锁屏后      立即（蓝）▸       [ ● ]
```

- 值：灰 = 跟随全局，蓝粗 = 自定义；点值弹层可改（`-1` = 跟随全局）。
- 开关显示值 = `participate && 全局该链路开关`（**裁决值**，不是原始配置）。
- 打开开关时若全局对应链路没开 → 自动打开全局并 toast「已同时打开全局「X」」（v1.26.5 补的联动，避免「纳入」悬空）。
- 关开关 / 调大延迟 = 削弱 → 先过验证闸门（`VerifyGate.bulkRequirement`）。

### 4.5 总开关的快照语义

`setAllLinks(false)`：三条一起关，并把当时的三条状态存进 `lastOnScenes`。
`setAllLinks(true)`：若快照里有任意一条为开 → 按快照原样恢复；否则三条全开。

关掉任一条链路时，会顺带清空 `pendingRelock`（否则「关了开关还会被锁回」）。

### 4.6 自动锁闭自检清单

- [ ] 全局某条链路**关** → 界面级该行开关必须跟着变灰/变关（显示值走裁决）。
- [ ] 界面级关掉一条 → 其它两条**不受影响**（关闭必须写到底，只影响这一条）。
- [ ] 点「解锁界面」**不能**改变任何自动锁闭配置（锁态 ≠ 参与态）。
- [ ] 只开「解锁后」时，正在前台使用的 App **不会**被到点锁掉（前台保护补查）。
- [ ] 延迟 > 0 的锁屏链路：熄屏后中途亮屏 → **不锁**。
- [ ] 关掉某条链路后，已经在等待中的待锁项**不会**再执行。

## 5. 解锁验证（`VerifyGate`）

### 5.1 四种方式

| mode | 说明 |
|---|---|
| `delay` | 等待 N 秒（默认 5 秒；输入侧放开，只做防溢出的上限） |
| `password` | 输入指定密码 |
| `quiz` | 连续答对 N 题（1–10） |
| `random` | 显示随机码（4–12 位），要求**手动输入**（自律：打断肌肉记忆） |
| `none` | 无需验证 |

### 5.2 三级优先级（择一，不是叠加）

```
界面级（LockRule.verifyMode）
  → 应用级（AppVerify，pkg 级默认值）
    → 全局（VerifyGate.globalRequirement）
```

每层 `null` 就下探一层；命中哪层就用哪层的参数。层内参数缺失按该层规则回退：选了「密码」但没填密码 → 退回「等待」（不会放行，也不会报错卡死）。

> 旧实现在批量场景里**无条件叠加**全局条件，导致「明明给这个界面单独设了等待，解锁却还要输密码」。现在是 `requirementFor()` 一条链路解析。

### 5.3 允许解锁时段（自律闸门）

`unlock_window_enabled` + 起止分钟。支持**跨午夜**（如 22:00–07:00）；`start == end` 视为全天允许。不在时段内 → 验证一律不通过（不是「跳过验证」，是「不许解锁」）。

### 5.4 批量解锁取「最强条件」

`bulkRequirement(ctx, rules)` 会把涉及的所有界面条件合并成一条「必须全部满足」的 Requirement（密码集合取并集、等待取最大、题数取最多）。所以批量解锁**永远不会比单条宽松**。

### 5.5 削弱性动作统一要过闸门

以下动作属于「削弱自律约束」，执行前必须先通过验证（加强性动作不需要）：

- 关掉自动锁闭的任意开关；把延迟**调大**；
- 解锁某个界面 / 批量解锁 / 删除已锁定的条目；
- 停用场景 / 提前结束专注（`strict` 时）/ 移除限额。

统一入口：`VerifyGate.requirementFor(...)`（单条）/ `bulkRequirement(...)`（批量）/ `requirementFor(pkg)`（应用级）。

## 6. 每日限额（`QuotaState` + `QuotaService`）

- 配置在**条目**上（`LockRule.quotaMin`），但生效粒度是**包**：同一包多条规则取**最大值**。
- `QuotaService`：前台服务，亮屏时每 **60 秒** 统计一次当日使用时长（`UsageTracker` + `UsageStatsManager`），熄屏暂停，没有限额配置自动退出。
- 超额 → `QuotaState.markOver(pkg)` + `StreakStore.markBroken()`（记为破功）→ `writeRules()` 把该包**整包**写成 `p` 条目，跳转目标换成 `QuotaGateActivity`。
- 用户点图标看到的是「额度已用完」而不是「点了没反应」——这是刻意的：静默拦截会被误解成 App 坏了。
- 跨天 `resetIfNewDay()` 惰性重置（读的时候发现日期变了就当空集）。
- 验证通过后可以单独 `clearOver(pkg)` 解除当日超额。

## 7. 专注会话（`FocusState` / `FocusEngine` / `FocusService`）

- 两种模式：`selected`（锁定勾选的 App）/ `whitelist`（锁定**除白名单外**的全部第三方应用，自动排除本 App、桌面、系统应用）。
- 启动时把目标包**固化**进 `focus_state.json` 的 `targets`，会话期间写 `p` 条目整包拦截（`r` 为空 = 纯拦不跳）。
- 结束条件：服务倒计时 / Alarm / 打开 App 对账，**任一先到**即清 targets 并恢复原状。
- `strict = true`：提前结束必须通过验证（无验证配置时强制答题）。
- 破功回流：提前结束记 `lastEarlyEnd`，工作台在 48 小时内显示「上次专注提前结束了——没关系，重新开始一次？」
- 工作台「一键专注」卡：直接按 `lastConfig` 重启上次配置，不用重进设置页。

## 8. 场景 与 定时计划

### 8.1 场景（`SceneStore`）

- 一个场景 = 一组方案 id（`presetIds`）+ 名字 + `active`。
- 启用：逐个成员应用方案（锁定 + 跳转）；停用：成员 App 全部解锁。
- `active` 与真实锁态之间没有自动同步——启用时写 true，停用时写 false，**由动作写入，不做反推**。
- 停用要过验证（`SceneEngine.deactivateRequirement`）。

### 8.2 定时计划（`ScheduleStore`）

- 多计划并存，**任一启用计划处于时间窗内**即视为「计划内」。时间窗支持跨午夜（23:00–07:00）。
- `weekdays` 为 `null` = 每天；否则 1=周一…7=周日。
- **进窗快照、退窗恢复**：进窗时记下当前上锁状态，退窗时按快照还原，避免覆盖用户在窗口外的自由配置。
- 与锁定强度联动：开了「计划窗口内禁用临时解锁」后，计划生效期间全局豁免不再下发（`writeRules` 里判 `noExemptInSchedule && anyActive`）。

## 9. 到点跳转（`SessionStore`）

对标「自律石头」的自动跳转：打开「触发 App」连续 N 分钟后，自动拉起「目标 App」。

| 字段 | 含义 |
|---|---|
| `pkg` | 触发 App |
| `target` | 目标 App（包名 → App 侧解析成启动组件；也接受深链 / 组件名） |
| `limitMin` | 连续使用多少分钟触发 |
| `maxJumps` | 当日第 N 次跳转后**锁定该 App**（0 = 不启用，次日自动恢复） |
| `graceSec` | 离开宽限：切到别的 App 后在此时间内回来接着算，超时重新计时 |
| `mode` | `jump` = 到点跳转（软引导）；`lock` = 连续刷满直接当日锁定 |

- 计时在 **Watcher** 里做（App 端算不准，且进程随时可能被杀）；前台一切换即清零（宽限期除外）。
- `mode = lock` 时 `t` 留空也要下发（纯锁定无跳转）。
- 已超额 / 专注中的包跳过本层（有更严的拦截，不需要软引导）。

## 10. 锁定强度 与 临时解锁

`LockStrength`（SP `lock_strength`）——每一项都在堵一条「合法绕过」的路：

| 项 | 说明 |
|---|---|
| 临时解锁时长 | **存秒**（`temp_unlock_sec`），输入侧可填秒/分/时；上限 `100_000_000` 秒只是防溢出，不是业务限制 |
| 每日次数上限 | `-1` 不限 / `0` 禁用 / `N` 每天 N 次；计数**全局**（一次临时解锁 = 1 次），跨日归零 |
| 计划内禁用豁免 | 计划生效期间临时解锁无效（四处共用同一判据：`writeRules` 不下发 / `TempUnlockActivity` 进门拦 / 磁贴 `onClick` 不放行 / 磁贴 `refresh` 置灰） |

临时解锁的真实语义：**一次动作把所有锁定界面一起放行**，不做「按包」豁免——所以计数必须是全局的。

## 11. 界面结构与各页功能

### 11.1 导航

底部 4 个顶层 Tab：**收藏（工作台）/ 应用 / 统计 / 设置**。其余全部是二级页（`Screen` 栈式导航，返回键出栈；顶层切 Tab 时替换栈顶而不是压栈）。

```
Screen = Favorites | Apps | Stats | Settings            ← 顶层，显示底部导航
       | Connection | SchemeLibrary | Inspector | History | Verify
       | Presets | Schedules | Quota | Scenes | Focus | Admin
       | LockStrength | AutoRelock | Detail(pkg)        ← 二级
```

### 11.2 工作台（`FavoritesScreen`，收藏 Tab）

顶部一行：标题「工作台」+ 搜索 / 多选 / 宫格↔列表 / 刷新 / 更多菜单。

**状态条（`QuickPanel`）**：`已锁定 N 个界面`（左）+ `今日拦截 N 次`（右，>0 用警示色）+ 场景一键切换卡（横向滚动，60dp 高大按钮，启用态 = 填充 + 2dp 边框 + 实心圆点）。

**分组**：`全部 / 自定义分组… / ＋ 管理` 横向 FilterChip。多选模式下「分组」按钮可批量分组、移出、新建、管理。

**两种视图**：

- **宫格**（默认，`GridCells.Adaptive(92dp)`）：图标 + 名称 + 状态。状态语言统一成「🔒 数字」：`🔒 N`（全锁）/ `🔒 x/y`（部分）/ `🔓 未锁` / `🔓 临时解锁 N分`。点开 = 该 App 的详情弹窗。
- **列表**：按包分组，`GroupHeader` 显示「N 个界面，已锁定 M 个」+ 展开箭头；行内是 名称 / 类名（等宽）/ `↗ 跳转：uri` / `🔓 解锁 <条件> ▸`（可点，直达解锁条件弹窗）/ 编辑 / 删除 / 锁定开关。

**空状态**：「还没有收藏任何界面」+ 引导去应用页或方案库。

**FAB（雪花）**：可拖动（位置会话内记忆，默认右下）。有解锁态 → 「一键冻结」全部锁上；全锁定 → 「全部解锁」（需验证）。

**更多菜单**：锁定可见 / 解锁可见 / 全部锁定 / 全部解锁 / 锁定默认分组。「可见」= 当前分组 + 搜索过滤后的结果；若有多选则只作用于选中项。

**宫格详情弹窗（`GridDetailDialog`）**：头部 `图标 + 名称 + 已拦截 x/y 个界面`；每个界面两行——第一行 `备注/类名 + 锁定开关`，第二行四个图标按钮（解锁条件 / 编辑 / 自动锁闭 / 删除）。**点标题行 = 编辑该条目的备注与跳转**（这是填跳转的入口，宫格开关只管锁态）。

### 11.3 应用（`AppsScreen`）

搜索框（App 名称 / 包名 / 界面类名）+ 已安装应用列表，点进 `Detail(pkg)` = `ActivityListScreen`：该 App 所有 Activity 的 `ActivityToggleRow`（标出 `isLauncher` 的桌面入口）。这是**新增锁定条目**的入口。

### 11.4 统计（`StatsScreen`）

读 `BlockStats`（Watcher 每 ~20 秒把计数写到 `blocked_stats.json`）：今日拦截次数、累计、按 App 分布、按日趋势、最近拦截明细。数据源在外部存储，需要 Shizuku 才能读。

### 11.5 设置（`SettingsScreen`）

五组：

| 组 | 条目 |
|---|---|
| 核心自律 | 解锁验证、锁定强度 |
| 自动执行 | 自动锁闭、定时计划 |
| 专注与限额 | 专注会话、时长限额、场景模式 |
| 方案与工具 | 方案库、锁定历史、Activity 查询、URL Scheme 库 |
| 系统 | 连接（副标题实时显示 Shizuku 状态）、防卸载保护 |

页面底部固定显示版本号。

### 11.6 磁贴

| 磁贴 | 服务 | 行为 |
|---|---|---|
| 全部上锁 | `LockAllTileService` | 把收藏夹里当前解锁的界面全部锁回 |
| 全部解锁 | `UnlockAllTileService` | 全部解锁（需验证） |
| 临时解锁 | `TempUnlockTileService` | 写入全局豁免；受每日次数与「计划内禁用」约束，不可用时会置灰 |

- 长按磁贴 → `ACTION_QS_TILE_PREFERENCES`。落地页 `TilePrefsActivity` 必须带 **`category=DEFAULT` + `priority=999`**：系统发的是裸隐式 intent，HyperOS 上会和 settings / permissioncontroller 等一起命中，只有优先级严格最高才唯一直选，否则弹「选择要使用的应用」。

## 12. 系统边界与已知限制

| 限制 | 说明 | 影响 |
|---|---|---|
| 必须 Shizuku | 无 root，所有系统动作经 Shizuku | 未授权时只能看配置，锁不上 |
| HyperOS 限制 `pm disable` | 组件禁用常被系统拒绝 | 自动降级为拦截模式（仍能拦，但图标还在） |
| Watcher 需常驻 | shell 进程被杀后要重拉 | 全都不拦时**先 `am force-stop` + 重开 App**，不要急着判定产品 bug |
| 通知重要性 | 系统可能把「自动锁闭」渠道设为 `importance=NONE` | 前台服务通知看不见（功能仍生效） |
| `pendingRelock` 是内存态 | 进程被杀后计时丢失 | 重启后不会补锁已解锁的界面 |
| 前台查询靠 `dumpsys` | 解析 `mCurrentFocus` / `mResumedActivity` | 系统改格式则前台保护失效（需回归） |
| 使用时长依赖「使用情况访问」 | `PACKAGE_USAGE_STATS` 是特殊权限，需手动授予 | 未授权时限额统计为 0 |

**测试纪律（血泪）**：验证拦截**绝不能用 `monkey`**——它每次运行都会抢占 `IActivityController` 且不释放，结果所有应用看上去都「没拦住」，极易误判为产品缺陷。一律用 `am start -n <pkg>/<cls>`。

## 13. 真机自检清单

**锁定与解锁**

- [ ] 工作台锁一个界面 → 图标消失（pm 模式）或点击被拦（block 模式）。
- [ ] 解锁后条目仍在列表里，可一键再锁。
- [ ] 锁定的界面，批量「全部解锁」需要验证。
- [ ] 填了跳转的条目：点图标直接到深链页，不是「点不动」。
- [ ] 带 `lockUntil` 的条目到期后自动放行。

**自动锁闭**

- [ ] 三条链路分别单独打开都能生效（互不依赖）。
- [ ] 界面级关掉一条 → 只影响那一条。
- [ ] 界面级延迟自定义后，实际按自定义延迟执行（不是全局值）。
- [ ] 前台正在用的 App 不会被「解锁后」链路到点锁掉。
- [ ] 熄屏延迟期间亮屏 → 不锁。
- [ ] 解锁界面**不会**改变自动锁闭配置（重复验证一次）。

**验证 / 限额 / 专注 / 跳转**

- [ ] 界面级「等待」优先于全局「密码」（不会被叠加成要密码）。
- [ ] 允许解锁时段外，任何验证都不能通过。
- [ ] 额度用完 → 点图标进 `QuotaGateActivity`，不是静默无反应。
- [ ] 专注 `whitelist` 模式不会误锁桌面与本 App。
- [ ] 到点跳转：切走再回来在 `graceSec` 内接着计时，超时重新计时。

**界面**

- [ ] 深色模式下所有卡片、弹窗、文字对比度正常。
- [ ] 长文案单行省略，不出现逐字竖排。
- [ ] 开关显示值 = 实际裁决结果（不允许「亮着但不生效」）。

### 14.2 新增的能力

| 新增 | 位置 |
|---|---|
| 工作台分组（全部 / 默认 / 自定义 + 批量分组） | `GroupStore` + `FavoritesScreen` |
| 多选批量（锁定 / 解锁 / 分组 / 全选） | `FavoritesScreen` |

| 界面级自动锁闭改为场景行（参与否决 + 延迟覆盖） | `FavoritesScreen` 的 `relockCfgRule` 弹窗 |
| 打开界面级开关自动打开全局链路（v1.26.5） | 同上，带 toast |

### 14.3 仍然跨版本有效的铁律

1. **开关显示值 = 实际裁决结果**。亮着就必须真的会锁；「已配置」类函数只能用于文字提示，不能当开关值。
2. **裁决只有一个入口**：自动锁闭走 `AutoRelock.lockSec() >= 0`，验证走 `VerifyGate.requirementFor()`。
3. **关闭要清干净**：关链路时同步清 `pendingRelock`；关总闸时一并关三条。
4. **锁态 ≠ 参与态**：解锁界面不得改动任何自动锁闭配置。
5. **更细层压过更粗层必须可见**：界面级单独关掉某条链路时，弹窗里一眼能看出来（开关灰 + 值显示「跟随全局」/明确的自定义值）。
6. **削弱性动作先验证，加强性动作不验证**。
7. **失败必须可见**：`LockOutcome.detail` 要传到 UI，自动锁闭失败要改通知文案。
8. **时长输入统一走 `DurationField`**：切换单位保持数值不变，不做范围限制，落盘绝不取整。
