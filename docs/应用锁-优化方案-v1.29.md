# 应用锁优化方案 v1.29

> 基线：v1.28.1 / code 95（git `923c05d` + `5a5a642`）
> 输入：代码静态核查（WatcherMain / AmsController / AutoRelock / AutoRelockService / LockEngine / QuotaState / UsageTracker / BootReceiver）
> 修订记录：v1 含过渡页 → **v2 取消过渡页**（会增加打开入口）→ **v3 新增「自我约束体系」并提到最高优先级**（用户主诉：控制不住自己关闭解锁）

---

## 0. 问题定义

两个观察：

1. 跳转搜索页配好之后，App 实际上是搜索工具，不需要限制使用时长。
2. 更大的问题：**控制不住自己关闭解锁**；但解锁强度太高，又怕应急情况用不了。

### 0.1 它们指向同一个根因

这个 App 是自用的——**同一个人既是设锁的人，也是破锁的人**。所有自助型自控工具的根本困境都在这里：没有第二个人保管钥匙。

现有系统的全部防线都在防「打开 App」，**没有一条在防「关闭锁」**。而关锁是成本最低的路径：一次验证，永久生效。相比之下，「打开被拦的 App」每次都要付出代价。人会本能地走阻力最小那条路，所以「关掉开关」永远比「忍住不点」更容易。

### 0.2 为什么「提高验证强度」不是答案

- 验证是**一次性**的：闯过一次就永久解锁，冲动只需要赢一次。
- 强度越高，应急成本越高 → 越怕用不了 → 在「不够狠」和「不敢用」之间反复横跳。
- 真正的差别不在「验证有多难」，而在**冲动和紧急的时间特征完全不同**：冲动峰值 10–20 分钟就消退，真正的紧急不会消退。

**所以要用时间区分，而不是用难度区分。**

一句话：现在的系统是在跟冲动比谁更快，应该改成让冲动自己过期。

## 1. 自我约束体系（新增，最高优先级）

五条机制，前两条是主干。

### 1.1 冷静期：削弱类操作不立即生效

把「改配置」的动作分成两类：

| 类别 | 例子 | 处理 |
|---|---|---|
| **加强类** | 加锁、缩短延迟、加名单、开计划 | 立即生效，零摩擦 |
| **削弱类** | 关自动锁闭总开关、关界面参与、永久解锁、移出名单、调大延迟、放宽锁定强度 | **预约执行，冷静期 2 小时** |

流程：

```
点「关闭自动锁闭」
  → 弹层：["2 小时后生效"（默认） / "现在就要"（走紧急通道）]
      → 选默认：写入 pendingChanges
                 开关仍显示「开」，副标题「2 小时后关闭 ｜ 撤销」
      → 选现在：进 1.2 紧急通道
```

规则：

- **方向不可逆**：一旦预约，只能撤销，不能改成「立即生效」，除非走紧急通道。
- 到点自动执行；期间任何时刻撤销，免费、无需验证。
- **开关显示值必须等于当前实际生效值**（跨版本铁律）。预约期间显示的是「仍开着」，副标题说明未来动作，不能显示成已关闭。
- 新装用户默认冷静期 2 小时，可调 1/2/6/24 小时，**但不能设为 0**（设为 0 等于关掉整个机制）。

实现：新增 `core/WeakenGuard.kt` + `files/cooldown.json`。

```kotlin
enum class Op { RELOCK_MASTER, LINK_PARTICIPATE, UNLOCK_PERMANENT, REMOVE_TARGET, RAISE_DELAY, LOOSEN_STRENGTH }

object WeakenGuard {
    fun isWeaken(op: Op, old: Any?, new: Any?): Boolean
    fun request(ctx: Context, op: Op, target: String, apply: () -> Unit): Outcome
    // Outcome = Applied | Scheduled(at) | NeedsEmergency(reason)
    fun tick(ctx: Context)                 // 到点执行，由 AutoRelockService 的 tick 驱动
    fun cancel(ctx: Context, id: String)
    fun pending(ctx: Context): List<PendingChange>
}
```

**覆盖面（MVP 只做三个口子，其余后续）**：

| 优先级 | 口子 | 说明 |
|---|---|---|
| MVP | 自动锁闭总开关 | 一次关掉全部自动回锁，危害最大 |
| MVP | 界面/应用永久解锁 | 冲动时最常点的按钮 |
| MVP | 移出名单 | 等同于永久解锁，但更隐蔽 |
| 后续 | 调大延迟、放宽锁定强度、关计划 | 危害小一档，但也要逐步纳入 |

### 1.2 紧急通道：给冲动一个合法出口，但这个出口有配额

不给出口是行不通的——用户会去找更彻底的口子（关开关）。所以必须有一个「快、但有代价、会自己关上」的通道。

| 项 | 设计 |
|---|---|
| 触发 | 冷静期弹层里选「现在就要」 |
| 前提 | 过一次验证（答题/输入/等待任一，按现有验证体系） |
| 代价 | 消耗「紧急额度」：**每周 3 次**（可调 1–10） |
| 效果 | **只放行指定 App 30 分钟**，到点自动恢复，不需要用户再操作 |
| 额度用完 | 只能等冷静期，没有第三个口子 |

关键点：**紧急通道不解锁配置，只临时放行**。所以不存在「用完忘了锁回去」的问题，也不需要用户记得恢复。

这一条可以直接复用现有能力，几乎不用新代码：

- 时长/次数：`LockStrength.tempUnlockSec` / `tempUnlockAllowed` / `recordTempUnlock`（已有，口径统一在 `UnlockExemptions`）
- 到点恢复：`GLOBAL_EXEMPT_UNTIL` 机制（已有，watcher 侧自动放行到期）
- 计划内禁豁免：`noExemptInSchedule`（已有）

需要新增的只是：把「紧急通道」的入口从设置页深处，提到「冷静期弹层」和「解锁按钮」旁边。

### 1.3 解锁语义改造（这一条最省事、收益最大）

现在点「解锁界面」= 永久解锁：

```kotlin
// LockEngine.unlock()
AppStore.updateLocked(pkg, cls, false)   // ← 永久生效
```

改成两级：

| 按钮 | 行为 |
|---|---|
| 「用 30 分钟」（主按钮，大） | 临时放行，走 1.2，扣紧急额度，到点自动锁回 |
| 「永久解锁」（二级菜单，小） | 走 1.1 冷静期 |

这样**冲动时顺手点到的那个按钮，自动变成有配额的临时通行证**。用户不需要理解「临时解锁」和「解锁」的区别，他只需要知道「我要用一下」。

同时这也解决了「锁定强度太高不敢用」：30 分钟放行不打乱配置，用得心安。

### 1.4 应急白名单：让大部分紧急需求根本不存在

绝大多数「紧急情况」集中在少数几类 App 上。它们永远不参与任何锁，不消耗额度，不需要验证。

内置默认：电话、短信、相机、时钟、日历、地图、支付类（微信/支付宝/云闪付）、健康码/政务类。

- 新建 `core/EmergencyWhitelist.kt`，内置默认 + 用户可增删
- 在 `writeRules()`（跳过下发给 watcher）与 `QuotaService`（跳过统计）**两处统一排除**
- 设置页显示当前名单，可加不可减（默认项不可移除，避免冲动时删掉）

这一条的意义：**减少「必须解锁」的场景**，比事后补救有效得多。

### 1.5 保护模式：隐藏削弱入口

开启后：

- 设置页里所有削弱类开关**不渲染**（不是置灰，是整个不出现）
- 管理入口改为「长按页面标题 3 秒 → 验证 → 进入」
- 首次开启时提示「开启后关闭需要走冷静期」

理由：冲动时人是按位置记忆点按钮的，看不到就点不到。这是渐进披露和反冲动的结合。

### 1.6 关于「搜索工具不需要限制」

这个判断我认同，而且现在的配置已经实现了它——**只要不给这些 App 设时长/次数配额，它们就只是搜索工具**。

但要诚实指出两点边界：

1. **搜索页放行 ≠ App 内没有信息流**。从搜索结果点进去的内容页，通常是同一个 Activity 内的路由切换，界面级拦截看不到，拦不住。
2. 所以真正的区分不是「搜索页 vs 信息流」，而是 **应用类别**：工具型（酷安、知乎、浏览器、地图）本来就不该设配额；消费型（抖音、小红书、微博）才设。

建议在 `GroupStore` 增加一个标签维度：

```kotlin
enum class AppKind { TOOL, CONSUMER }
```

- `TOOL`：不参与次数配额、不参与等待页，只保留「点图标进搜索页」
- `CONSUMER`：参与次数配额与等待页

这样「限制」只落在真正消耗时间的地方，不会误伤工具。

### 1.7 与现有验证体系的关系（重要简化）

改造后验证的使用场景只剩一个：**紧急通道准入**。

| 场景 | 改造前 | 改造后 |
|---|---|---|
| 关开关 / 永久解锁 | 验证一次，立即生效 | 冷静期 2 小时（无需验证） |
| 临时用一下 | 设置页深处的临时解锁 | 主按钮「用 30 分钟」+ 验证一次 |
| 应急 | 无明确路径，只能去关开关 | 紧急通道，验证一次，30 分钟自动恢复 |

这就是「解锁强度高怕应急用不了」的正解：**平时根本不需要验证（等待本身就是最强的验证），只有紧急才验证，而且只需一次、只需 30 秒。**

### 2.2 S9 详查：为什么 30 分钟必然失效

```kotlin
// core/AutoRelock.kt:261 —— 纯内存，不落盘
var pendingRelock by mutableStateOf<Map<String, Long>>(emptyMap())

// core/AutoRelockService.kt:48 / 54 —— 同样是内存 HashMap
private val exitPending = HashMap<String, Long>()
private val screenOffPending = HashMap<String, Long>()
```

`onStartCommand` 返回 `START_STICKY`，被杀后系统会重建服务——但重建后三张表全是空的。

| 延迟 | 30 分钟内被杀的概率 | 结果 |
|---|---|---|
| 5 分钟 | 低 | 通常能锁上 |
| 15 分钟 | 中 | 偶尔失效 |
| 30 分钟 | 高（HyperOS 清理常见 10–30 分钟一档） | 基本不生效 |
| 60 分钟以上 | 几乎必然 | 必然不生效 |

**不是「必须后台」的问题**——前台服务在跑也保不住那张表。根因是把「计时」放在最容易被杀的地方，而「拦截」放在最不容易被杀的地方（watcher 是 shell 进程）。

叠加 S10：中途任何一次亮屏都会让「熄屏后」计时归零重来。两个因素同时作用，就是「怎么设都不生效」。

### 2.3 修复方案

**S9：待锁表落盘 + 精确闹钟双保险**

1. 三张表写入新 SP（`relock_pending`），每项存 `(wall, elapsed)` 双时间戳，判定取「两个都没到时才算未到」，同时抗进程重启与时间回拨。
2. 每项加 `AlarmManager.setExactAndAllowWhileIdle(RTC_WAKEUP, deadline, → AutoRelockService)`。进程被杀，闹钟把服务叫起来。
3. `onCreate` 从 SP 恢复待锁表，重新对齐闹钟（已过期的立即处理）。
4. Android 12+ 需 `SCHEDULE_EXACT_ALARM`；设置页检测 `canScheduleExactAlarms()`，未授权红字提示（HyperOS 同时提示允许自启动）。
5. **不改锁的执行路径**：到点仍走 `LockEngine.apply(lock=true)`，只换「谁来叫醒它」。

不选「把计时下沉到 watcher」，是因为那要让 watcher 直接改 App 的 `rules.json`，会引入「界面显示解锁、实际被拦」的新假开关风险。闹钟方案只动计时层，行为等价、可回滚。

**S10：改语义，不放弃**

亮屏不清表，只暂停推进；再次熄屏保留原时刻。语义从「连续熄屏 30 分钟」改为「熄屏累计 30 分钟」。

| 缺陷 | 修法 | 落点 |
|---|---|---|
| S1 | `BootReceiver` 加 `AmsController.ensureStarted()` | `core/ScheduleWorker.kt:42` |
| S2 | `LAST_RULES_RAW = raw` 移到解析成功之后；catch 改 `log("reload parse error: " + t)` 并保留旧规则 | `watcher/WatcherMain.java:393` |
| S3 | 原子写：`.tmp` → `renameTo` | `core/AmsController.kt:97` |
| S4 | 启动失败重试 5 次 / 每次 2 秒，仍失败才退出并写 `al_watcher.fail` | `watcher/WatcherMain.java:299` |
| S5 | 新增 `WatcherGuardService`（前台服务，60 秒 tick，`isRunning()` 为假就拉起） | 新增 `core/WatcherGuardService.kt` |
| S6 | 每 tick 记 `(wall, elapsed)`，`abs(Δwall − Δelapsed) > 120s` 判为跳变 | 新增 `core/TimeJumpStore.kt` |
| S7 | 守护服务启动时比对 `watcherUpToDate()` | 复用 `AmsController` |
| S8 | `killOtherWatchers()` 只杀同 APK 路径的旧实例 | `watcher/WatcherMain.java:100` |

## 3. 访问摩擦（次要，只对消费型 App）

这一章解决「减少打开频率」，与 §1 的「阻止关锁」是正交的两件事。**只需要对 `AppKind.CONSUMER` 生效**。

### 3.1 三个杠杆

**次数配额（主手段）**：每个消费型 App 每天 N 次点图标机会（建议 10，可配 1–50）。第 N+1 次起连搜索页都不给，直接拦回桌面。时间配额管不住「一天点开 40 次、每次 3 分钟」，只有次数能管住频率。

**无决策延迟**：点图标后过一个等待页——只有倒计时数字和进度环，**没有任何可点元素**，唯一出口是返回键（回桌面）。到点自动执行原动作。用户不需要做决定，所以它不是入口，只是把 0.2 秒的响应拉长到 N 秒。

**递增惩罚**：第 1 次 3 秒，第 2 次 5 秒，第 3 次 10 秒，第 4 次起 20 秒。`delay = min(base × 2^(n-1), cap)`。

### 3.2 实现

不能在 watcher 线程 sleep（`activityStarting` 是 AMS 同步回调，阻塞会 ANR）。插一个透明 `HoldActivity`：

```
activityStarting 命中 → 拉起 HoldActivity（带 dl / at）→ return false
HoldActivity 倒计时 N 秒（noHistory / excludeFromRecents / 无按钮）
  → 到点 startActivity(原目标) → finish()
```

| 位置 | 改为 |
|---|---|
| `WatcherMain.java:835` 无 redirect | 拉起 `HoldActivity`（`at` = App 侧算好的秒数） |
| `WatcherMain.java:852` 有 redirect | 拉起 `HoldActivity`（带 `dl`，倒计时后再跳） |
| `WatcherMain.java:800` 包级超额 | **保持立即拦**，`QuotaGateActivity` 保留 |

等待秒数由 App 侧算好写进 `cfg` 段，watcher 只透传：

```json
{"cfg":{"hold":[3,5,10,20],"opens":{"com.x":[7,10]}}}
```

调参不动 watcher，不用每次 bump 版本。

### 3.3 边界

| 风险 | 处理 |
|---|---|
| 等待页被从最近任务切回 | `excludeFromRecents` + `noHistory` + `onStop` 即 finish |
| 等待期间按电源键 | 按 `elapsedRealtime` 算，回来继续 |
| 等待页自己成为入口 | 页面上没有可点元素，返回键回桌面 |
| 等待后目标被自己的规则拦 | `SELF_JUMP_UNTIL` 在**拉起时**刷新（3 秒窗口不够覆盖 20 秒等待） |

## 4. 「省下的时间」

口径：不用「限额 − 实际」（那是没用到）。用同基线对比：

> 本周日均 47 分钟，上周 78 分钟，少 31 分钟（−40%）

数据全部来自 `UsageStatsManager`，`UsageTracker.todayMinutes()` 已有权限与取数代码，扩展到 7 天即可。

`StatsScreen` 在 streak 下插一块：日均对比 + 少刷总时长。「拦截次数」降级为副指标——它衡量的是挣扎，不是成果。

## 5. 配置备份 / 导出

9 个 JSON + 6 个 SP + 2 个外部文件，换机/刷机/误清数据全丢。导出单个 `backup.json`（带 `appVersion` / `schema`）→ SAF 保存；导入校验 schema 后逐文件写回，重启服务并 `writeRules()`。入口在设置页「系统」。不做云同步。

---

## 6. 时间回拨防护

新增 `TimeJumpStore`：每 tick 记 `(wall, elapsed)`，`abs(Δwall − Δelapsed) > 120s` 判为跳变，计划判定切到 `elapsed` 推算（以最后一次可信 wall 为锚）。不做「禁止改时间」，只做「改时间不产生收益」。

## 7. 结构性重构：EffectiveRules

### 7.1 现状

`AmsController.writeRules()`（31–99 行）用四段 if 合并五层：界面锁定 / 包级超额 / 专注会话 / 到点跳转 / 全局豁免。`WatcherMain` 单文件 875 行扛五件事。每加一个跳转类功能要同时改四处（`buildTargetIntent` / `startViaAm` / `validateRedirectTarget` / 测试按钮）——v1.28.0 漏 `WatcherVersion` 就是这么来的。

### 7.2 目标形态

```kotlin
// core/EffectiveRules.kt —— 纯函数，无 Android 依赖，可 JVM 单测
sealed interface Entry {
    data class Block(val comp: String, val redirect: String, val until: Long) : Entry
    data class PkgBlock(val pkg: String, val reason: Reason) : Entry
    data class Session(val pkg: String, val limitSec: Int, val target: String) : Entry
    data class Exempt(val until: Long) : Entry
    data class Cfg(val hold: List<Int>, val opens: Map<String, IntArray>) : Entry
}

enum class Reason { UI, QUOTA, FOCUS, SESSION, PLAN }

fun decide(
    rules: List<LockRule>, over: Set<String>, focus: Set<String>,
    sessions: List<SessionCfg>, exemptUntil: Long, cfg: FrictionCfg, now: Long
): List<Entry>
```

`writeRules()` 缩成「`decide()` → JSON → 原子写」；规则总览页直接 `decide()` 后按 `Reason` 渲染，**同一真源**。

### 7.3 分期

1. 四段 if **原样**搬进 `decide()`，12 条单测覆盖每层与层间冲突
2. `writeRules()` 消费 `decide()`，输出与今天**逐字节一致**（golden test）
3. 再做「生效规则总览页」

**验收判据**：改造前后各导一次 `blocked.json`，JSON 结构 diff 必须为 0。

## 8. 排期

| 批次 | 内容 | 理由 |
|---|---|---|
| **A1** | S9 + S1 + S2（三个 P0 止血） | 你直接踩到的「30 分钟失效」在这里，一次修完就能感知 |
| **A2** | 其余稳定性 S3–S8、S10 + 备份 + 时间防护 | 预防性，可紧随 |
| **D** | 自我约束体系 §1（冷静期 + 紧急通道 + 解锁语义 + 白名单 + 保护模式） | 你的主诉，但依赖 A1 的稳定性（冷静期到点执行要求计时可靠） |
| **B** | 访问摩擦 §3（只对消费型） | 降频，优先级低于 D |
| **C** | EffectiveRules + 总览页 | 还债 |

D 依赖 A1 不是形式上的：冷静期「2 小时后执行」本质上也是一张待执行表，**如果 S9 不修，冷静期会和自动锁闭一样失效**。所以顺序必须是 A1 → D。

每批都要：真机验证 → 确认 watcher 换代 → 装完息屏收尾。

## 9. 明确不做的

- 拦截后过渡页 / 「仍要打开」按钮：会增加打开入口
- 位置 / WiFi 触发：要常驻定位权限，收益低于上面几项
- 云同步 / 账号体系
- 社交 / 排行榜 / 番茄钟 / 白噪音
- 对工具型 App 设配额：与「搜索工具」定位冲突
