## 0. 总览

### 0.1 一句话分工

| 功能 | 一句话 |
|---|---|
| **锁闭**（手动锁定/解锁） | 把**某个界面**锁上或解开——双引擎执行（组件禁用优先，系统级拦截兜底） |
| **锁闭强度** | 给「临时解锁」这条合法通道上闸门——限时长、限次数、计划期内不给口子 |
| **自动冻结** | 在你不用的时刻把**整个应用**从系统里「消失」——图标消失、进程不可用（最彻底） |
| **自动锁闭** | 解锁后 / 退出后 / 锁屏后，把**锁过的界面**自动锁回去——图标保留、点击被拦 |

### 0.2 实际存在的五种「拦截强度」（从轻到重）

| # | 手段 | 粒度 | 机制 | 可见效果 | 谁在用 |
|---|---|---|---|---|---|
| 1 | 组件禁用 `pm disable-user` | 单个界面 | 系统把该组件标记为 `DISABLED_USER` | 该界面点不进去（无反应），图标保留 | 手动锁闭·引擎 A（首选） |
| 2 | 系统级启动拦截 `IActivityController` | 单个界面（可带跳转） | shell 常驻进程拒绝启动请求 | 被拒 + 可自动跳转（搜索页等） | 手动锁闭·引擎 B（兜底 / 跳转专用） |
| 3 | 整包禁用 `pm disable-user` | 整个应用 | 同上，包级 | **图标消失**、进程不可用 | **自动冻结** |
| 4 | 包级拦截（Watcher 的 `p` 规则） | 整个应用 | 启动请求被拒 → 拉起额度提示页 / 静默拒绝 | 整包打不开，可带提示页 | 时长限额、专注会话 |
| 5 | 全局豁免（Watcher 的 `g` 规则） | 全部 | 豁免期内放行一切启动 | 临时解锁 | **锁闭强度·临时解锁** |

## 1. 锁闭（核心锁定与解锁）

### 1.1 锁什么、存什么

- **锁定粒度 = 单个界面**：一条规则 = `包名 + Activity 类名`（`LockRule`）。
- 收藏夹（`rules.json`）是**唯一**的锁定清单；锁定即入夹，**解锁不删条目**（`locked=false`），随时可再锁。
- `LockRule` 关键字段：`block`（是否拦截模式）、`locked`（是否锁定）、`redirectUri`（跳转深链）、解锁条件（`verifyMode/verifyDelaySec/verifyPassword/quizCount`，null = 跟随）、`quotaMin`（每日限额）、`lockUntil`（锁定有效期）。

### 1.2 双引擎执行链（真正「锁上」的两种办法）

入口统一是 `LockEngine.apply(pkg, cls, lock, redirectUri)`：

| 分支 | 条件 | 执行 | 结果字段 |
|---|---|---|---|
| **跳转模式** | 该规则存在**有效跳转目标**（含历史已存） | ① 若组件之前被 pm 禁用 → 先 `pm enable` 恢复；② 写 `block=true + redirectUri`；③ 下发规则 + 确保 Watcher 运行；④ `am force-stop` 清任务栈 | `mode="block"` |
| **组件禁用（首选）** | 无跳转 | 依次尝试 4 种 `pm disable-user / pm disable` 命令变体，验证组件确实变为禁用 | `mode="pm"` |
| **系统级拦截（兜底）** | 组件禁用被系统拒绝（如 HyperOS 封锁 shell 改组件状态） | 写 `block=true`；下发规则；确保 Watcher 运行；`am force-stop` | `mode="block"` |
| 失败 | Shizuku 不可用 / 拦截进程起不来 | **回滚**（移除规则、重写清单），返回失败 | `mode="none"` |

三个关键细节（都有踩坑来历）：

1. **`force-stop` 清任务栈**：不清的话点图标只是「恢复已有任务」，不会走启动路径，拦截器就看不到请求。
2. **跳转必须走拦截模式**：组件被 `pm disable-user` 后，点图标**连启动请求都不产生**，拦截器收不到 → 任何跳转深链必然失效。所以有跳转的规则强制 `block=true` 且组件必须保持启用。
3. **保存跳转的唯一入口是 `LockEngine.saveRedirect()`**：它会按需把一条 pm 模式的条目自动切到拦截模式，杜绝「设置里存了跳转、实际不生效」。

### 1.3 拦截模式的运行链（Watcher）

- **进程**：`AmsController` 通过 Shizuku 以 shell 身份启动 `app_process` 常驻进程（WatcherMain），向系统注册 `IActivityController`（Android 留给自动化测试的全局启动控制器）。**每 2 秒**重载规则文件、**每 10 秒**重新注册一次（系统重启 / AMS 重启后自恢复）。
- **规则传输**：App 写外置 `blocked.json`，shell 读。`writeRules()` 一次性组装**五类条目**：

| 条目 | 字段 | 含义 |
|---|---|---|
| ① 组件规则 | `{"c":"pkg/cls","r":"跳转或空","u":到期毫秒}` | 只下发 `block && locked` 的收藏条目；`u` 存在 = 到期自动放行 |
| ② 超额整包 | `{"p":"pkg","r":"额度提示页"}` | 当日限额用完的 App，整包拒绝并送「额度用完」页 |
| ③ 专注整包 | `{"p":"pkg","r":""}` | 专注会话中目标 App 整包静默拦截 |
| ④ 到点跳转 | `{"f":包,"s":时限秒,"t":目标,"n":次数,"g":宽限,"m":模式}` | 连续使用 N 分钟 → 拉起学习 App / 直接锁定 |
| ⑤ 全局豁免 | `{"g":1,"u":截止毫秒}` | 临时解锁期间放行一切 |

- **拦截判定顺序**（`activityStarting` 内，自顶向下）：
  1. 会话计时（豁免期内跳过，休息时间不催学习）→
  2. **全局豁免**：临时解锁期内**放行一切**（优先于所有规则）→
  3. **到点跳转闸**：冷静期内切回 / 当日已收走 → 拦截并送目标 →
  4. 无任何规则 → 放行 →
  5. **包级超额拦截**：拒绝 + 额度页（0.6 秒重复启动去重）→
  6. **组件规则命中**：
     - `u` 到期 → 自动解除该条并放行（**锁定有效期**）；
     - 其余 → 拒绝；带跳转时按规则决定跳不跳：
       - **桌面点击（MAIN + LAUNCHER）永远立即跳转**，多少次都有响应；
       - 跳转落地后又被应用内部链路绕回被锁界面（非桌面来源）→ 判定深链无效，**抑制跳转 60 秒**（只拦不跳；改跳转目标自动解除）；
       - 0.6 秒内的重复启动合并去重。
- **统计**：每次拦截写入 `blocked_stats.json`（今日/累计/分 App/最近事件）。

### 1.4 跳转（搜索优先模式）

- 目的：点图标不再「没反应」，而是直达该 App 的搜索页（如 `snssdk1128://search?keyword=`）。
- **两个硬前提**：
  1. 规则 `block=true && locked`，且组件保持启用；
  2. 跳转必须配在**桌面入口界面**（launcher Activity）——点图标先进入入口，若入口被锁且没配跳转，请求在入口就被挡回，更深界面的跳转永远执行不到。界面列表会用 `getLaunchIntentForPackage` 判定并标注「桌面入口」。
- **跳转优先于自动冻结**：冻结（整包禁用）后无启动请求 → 跳转必失效。因此：
  - `AutoFreeze.targets / targetCount / freezeOne` 一律**排除已配跳转的包**；
  - 服务启动时 + 每 15 秒运行 `healJumpConflicts()`，把「已配跳转却仍处冻结态」的包主动解冻（自愈残留）；
  - 冻结页对冲突包显示红色提示卡「已配跳转 · 冻结后跳转失效」。

### 1.5 解锁（把锁去掉）

| 入口 | 流程 |
|---|---|
| 收藏页列表行 / 宫格弹窗 / 界面详情页 | 需验证时先过「该界面的生效条件」→ `LockEngine.apply(lock=false)`：恢复组件 → `locked=false` → 重写清单 → 记历史 → **通知自动锁闭开始计时**（`noteUnlocked`） |
| 磁贴「全部解锁」 | 先通过**全库最强条件**（`UnlockGateActivity` 全屏验证）→ 逐个解锁（条目保留） |
| 场景模式停用 | 先过 `deactivateRequirement`（相关界面的最强条件）→ 批量解锁 |
| 锁定有效期到期 | **无需解锁**：Watcher 到点自动放行该条目 |
| 删除条目 | 若条目仍处于锁定态且设了验证 → 先过验证再删 |

解锁一律**保留收藏条目**——条目是自动锁闭的管辖依据，删掉就退出了管辖。

### 1.6 解锁验证（VerifyGate）

- **五种方式**：无需验证 / 等待倒计时（自定义秒/分/小时，无范围限制） / 密码 / 答题（1–10 题连对） / 随机密码（4–12 位）。
- **三级条件（择一，不叠加）**：**界面级 > 应用级 > 全局**。每一层「未设置」就下探一层；命中哪层用哪层的参数（该层参数缺失按层内规则回退，如选了密码但没填 → 退回等待）。
- **批量场景取「最强」**（磁贴全解锁、场景停用、关总闸等）：
  随机密码 > 密码 > 答题 > 等待；密码**任一可接受**；等待取最长。全部无已锁界面时才回退全局条件（否则等于无需验证）。
- **解锁时间范围**：可设「仅在 H1–H2 内允许通过验证解锁」（默认 22:00–07:00，支持跨午夜）；范围外验证一律不通过。防绕过修改（如关闭验证）不受此窗口约束（否则窗外形成死锁）。
- **单条规则未被单独设置时**自动跟随应用级、再跟随全局——同一 App 多个界面不必设 N 遍。

### 1.7 防绕过闸门（全 App 通用原则）

> **削弱约束的操作 → 必须先当场通过验证；加强约束的操作 → 直接执行。**

| 动作 | 方向 | 验证门槛 |
|---|---|---|
| 关闭」解锁验证」总开关 / 切方式 / 改密码 / 缩短等待 | 削弱 | 全库最强 |
| 解锁某个界面 / 删除受锁条目 | 削弱 | 该界面生效条件 |
| 自动锁闭：关总开关 / 全部关闭 | 削弱 | 全库最强 |
| 自动锁闭：关某个应用、关某条场景（应用级） | 削弱 | **该应用**范围最强 |
| 自动锁闭：关某条场景（界面级）/ 关界面行 | 削弱 | **该界面**自己的生效条件 |
| 自动锁闭：延迟**调大**（拖到 24h≈不锁） | 削弱 | 被改层级同粒度门槛 |
| 自动冻结：关开关 / 移出名单 / 解冻全部 | 削弱 | 全局最强 / 该应用最强 |
| 打开开关、调小延迟、立即锁回、加入名单、锁定界面 | 加强 | 不验证 |

口诀：**「关/放/拖 = 先验证，开/紧 = 直接走」**。门槛粒度必须与**被操作对象**同粒度——早期一律用全库最强，导致「关微信的开关被抖音的密码拦住」，已修正。

### 1.8 其它会改变锁定态的入口（汇总）

| 入口 | 行为 |
|---|---|
| 快捷磁贴 ×4 | 全部上锁 / 全部解锁（要验证）/ 全部锁闭（自动锁闭的紧急补刀，忽略参与开关）/ 临时解锁（豁免） |
| 场景模式 | 启用 = 批量上锁；停用 = 批量解锁（要验证） |
| 定时计划 | 时段内自动全部上锁，出时段恢复原状（15 分钟巡检 + 开机对账） |
| 时长限额 | 统计用量，超额 → 整包拦截 + 额度页；次日 0 点重置 |
| 专注会话 | 会话内目标 App 整包静默拦截 |
| 到点跳转 | 连续使用到点 → 跳学习 App 或当日锁定 |
| 息屏清栈 | 息屏时结束锁定中 App 的任务（封「点图标恢复任务」的绕过路径） |

## 2. 锁闭强度（设置 → 锁定强度）

### 2.1 定位

「每一项都在堵一条合法绕过路径」：临时解锁是自律 App 里最容易被滥用的口子（想玩就临时解锁），本页把它关进笼子。**本页不直接锁定，管的是「放行的额度」**。

### 2.2 三项配置（实际实现）

| 配置项 | 取值 | 默认 | 说明 |
|---|---|---|---|
| **临时解锁时长** | 预设 `5 / 10 / 15 分钟` + **自定义**（秒/分/小时自由输入，无范围限制） | 15 分钟 | v1.24.8 起数据层改存**秒**（新键 `temp_unlock_sec`，旧分钟键自动换算迁移；旧接口保留兼容）。v1.24.9 终检：删「30 分」预设（5 个选项一行溢出，「自定义」被裁）；上限放开到 `100,000,000` 秒防溢出（原 24 小时 = 回显 3 天存 1 天的静默改写）；下限 1 秒（与 `VerifyGate.safeDelaySec` 同口径） |
| **每日临时解锁次数上限** | `不限 / 3 次 / 1 次 / 禁用` | 不限 | **全局**计数（`tu_used_today` + `tu_date`，跨日自动归零），一次临时解锁记 1 次；`禁用=0` 直接拒绝。三处同步：设置页「今日已用 N / M 次」、磁贴置灰、验证页进门拦截。**（v1.24.9 修复前是死代码，详见 §6.3）** |
| **计划窗口内禁用临时解锁** | 开 / 关 | 关 | 定时计划（如睡眠模式）生效期间，临时解锁失效——半夜不给口子。同一判据**四处共用**：规则下发抑制（`AmsController`）+ 验证页进门拦（`TempUnlockActivity`）+ 磁贴点击不放行 + 磁贴置灰「计划生效中，临时解锁已禁用」。**（v1.24.9 终检前只有第一处 = 假动作，详见 §6.3）** |

### 2.3 临时解锁的运行链

```
临时解锁磁贴（钥匙）点击
  ├─ 正在豁免中？ → 立即全部落锁：清除豁免 + 对每个锁定包 force-stop 清任务栈
  ├─ 没有锁定中的界面？ → 磁贴置灰（不可用）
  ├─ 今日次数用完 / 已被禁用？ → 磁贴置灰（不可用）          ← v1.24.9 新增
  └─ 否则 → 全屏验证页 TempUnlockActivity
        ├─ 进门先过次数闸门（禁用 / 用完 → 只显示原因 + 「返回」，不进验证流程）
        ├─ 逐级展示验证（等待倒计时 / 密码 / 答题 / 随机 / 时间范围拦截提示）
        └─ 通过 → 写入豁免截止时间（now + 时长**秒数**，不做任何取整）
                  → 记 1 次临时解锁（当日计数 +1）              ← v1.24.9 新增
                  → writeRules()（下发 {"g":1,"u":…}）
                  → 回到桌面（用户自行选 App）
```

- **放行时长**取自本页「临时解锁时长」（秒级精度）：填 90 秒就放行 90 秒，不会被取整成分钟（v1.24.9 修复前会被整数除法砍成 1 分钟）。
- **豁免语义（Watcher 侧）**：豁免期内**放行一切启动**（优先于组件规则、包级超额拦截）；且豁免期内不累计「到点跳转」的连续使用计时（休息时间不催学习）。
- 豁免到期自动失效；豁免期内再点磁贴 = 立即恢复拦截（并 force-stop 各包任务栈）。
- 临时解锁**不改变锁定状态**（条目仍 locked），只是「放行窗口」——所以自动锁闭的到点回锁、自动冻结的锁屏冻结等系统行为**不会因为临时解锁而停摆**。

### 2.4 与「解锁验证」的分工

| | 解锁验证（设置 → 解锁验证） | 锁定强度（设置 → 锁定强度） |
|---|---|---|
| 管什么 | 想解锁（拿掉锁）时要过什么关 | 临时放行（不拿掉锁）的额度与限制 |
| 形态 | 五档方式 + 三级条件 + 时间范围 | 时长 / 次数 / 计划内禁用 |
| 关联 | 「临时解锁」本身也要**先通过最强解锁验证**，才进入豁免 | 临时解锁磁贴的执行链 |

两者在「设置」里同属**核心自律**分组。

## 3. 自动冻结（AutoFreeze）

### 3.1 定位与总则

- **对标「雹 / 冰箱」的整包冻结**：`pm disable-user --user 0 <包名>`，图标消失、进程不可用，是最彻底的戒断手段。
- **策略 = 白名单**：只有**加进冻结名单**的应用才有资格被冻（与自动锁闭的「黑名单式默认参与」正好相反）。
- **跳转优先**：已配跳转的包一律不冻（冻结后无启动请求，跳转必失效）——见 1.4。
- **防绕过同口径**：关开关 / 移出名单 / 解冻全部 = 削弱 → 先验证；打开开关 / 加入名单 = 加强 → 直接走。
- 全程仅走 **Shizuku** 通道。

### 3.2 两条触发链路

| 链路 | 触发 | 执行 | 说明 |
|---|---|---|---|
| **① 锁屏即冻** | `ACTION_SCREEN_OFF` | 立即冻结**全部**目标（`freezeAll()`） | 进程存活时由 App 内广播接收器直接执行（快路径）；进程不在则由常驻服务兜底 |
| **② 退出后延迟冻** | 名单内应用**离开前台** | 记下离开时刻 → 到各自延迟后冻结 | 轮询前台（每秒 1 次，`dumpsys window` + `dumpsys activity` 兜底，走 Shizuku，不需「使用情况访问」权限）；**中途回到前台则取消** |

- **延迟**：全局默认 **120 秒**；单应用可覆盖（`跟随全局` / 0–24 小时；0 = 离开后立即冻）。延迟上限 24 小时是**语义边界**（拖到 24h≈不冻），超限在 UI 明确报错而不是静默改写。
- **开机恢复**：`LockApp` 启动时按配置拉起守护服务，并刷新一次冻结态 + 自愈跳转冲突。

### 3.3 名单与保护

- **受保护包（永不冻结）**：本 App、Shizuku、`com.android.shell`、`android`、SystemUI、Settings、Phone、providers.settings、小米桌面、`com.android.launcher`、`launcher3` ——防止把设备或自己锁死。
- **跳转包自动排除**：`hasJumpRule(pkg)`（存在 `block && locked && redirectUri非空` 的规则）→ 不进 `targets()`、不允许 `freezeOne()`。
- **冲突自愈**：`healJumpConflicts()` 在服务启动时 + 每 15 秒执行，把「已配跳转却仍是冻结态」的包解冻。
- **移出名单即解冻**：`setAppEnabled(pkg,false)` 时顺带 `thawOne`，避免「忘了它还冻着」。
- **打开任一开关时先 `thawAll()`**：把名单内全部解冻，等待下一次触发（避免开关刚开就处于冻结残留态）。

### 3.4 冻结态展示

- `frozenNow` = `pm list packages -d` 结果 ∩ 名单（一次查询，比逐包查快）；
- 刷新时机：打开页面、每 3 秒轮询、解锁屏幕（`ACTION_USER_PRESENT`）、冻结/解冻动作后；
- 名单区标题显示 `共 N 个应用，已冻结 X 个`；若有被跳转排除的连带提示「另有 N 个配了跳转，已自动跳过冻结」；冲突包显示红色提示卡。

### 3.5 服务生命周期与省电设计

- 前台服务（通知 id 3001，常驻通知「自动冻结」，`START_STICKY`）；
- 唤醒条件：`active() = 开关开 && 名单非空`；`sync()` 负责启动/停止；
- 性能：前台查询与冻结动作**全部在后台单线程**（`scheduleWithFixedDelay`，上次跑完才排下次）；延迟用 `HashMap` 待冻表（pkg → 离开时刻），**不用 postDelayed**、不堆任务；名单空 / 开关全关 → 不查询（零开销）；屏幕熄灭期间不跑退出链路。

## 4. 自动锁闭（AutoRelock）

### 4.1 定位

- 与自动冻结的对照：**冻结**=整包禁用、图标消失；**锁闭**=走 `LockEngine` 重新上锁、图标保留、点击被拦。
- 执行路径与**手动上锁完全同一条**（`LockEngine.apply(lock=true)`），因此会自动保持既有跳转配置（`effectiveRedirect` 兜底读取已存跳转）。
- 语义：把「解锁过的界面」在合适的时机**自动变回锁定态**，弥补「解锁一时爽」的空窗。

### 4.2 三条触发链路（场景）

| 链路 | 触发 | 执行细节 |
|---|---|---|
| **① 解锁后** | 界面被解锁（`LockEngine.unlock` → `noteUnlocked` 埋点） | 记入待锁表 `pendingRelock`（key=pkg/cls，value=解锁时刻 elapsedRealtime）；服务每秒扫描，`现在 − 解锁时刻 ≥ 生效延迟` 即重锁。到点前会**补查一次当前前台**，目标包正处前台则放弃并清项（v1.24.10 修；修前只读另一条链路顺带维护的 `lastForeground`，用户只开本链路时这道保护形同虚设） |
| **② 退出后** | 目标应用**离开前台** | 每秒轮询前台；发现离开 → 记 `exitPending[pkg]`；到各自延迟 → 重锁**该包下全部已解锁、且仍参与本链路的界面**（v1.24.10 修；修前只锁该包第一条规则，一个包锁多个界面时会漏）；**中途切回 → 取消**（`exitPending.remove`） |
| **③ 锁屏后** | `ACTION_SCREEN_OFF` | **延迟 = 0**：立即重锁（App 进程内广播快路径 + 服务兜底）；**延迟 > 0**：记入 `screenOffPending`，到点且**仍处熄屏**才锁回；中途亮屏（`ACTION_SCREEN_ON`）→ **整批放弃** |

各链路的到点时刻都用**该链路自己的延迟**解析（三种场景各自独立，互不串值）。

### 4.3 管辖范围

> **管辖 = 收藏夹里所有已锁定（或曾锁定、现状 unlocked）的界面条目**。
> 三级名单（全局/应用/界面配置）只是「精细覆盖」，**不需要**逐条登记。

- 收藏夹里没有该条目 → 不管辖（自动锁闭只作用于用户主动锁过的界面）；
- 条目存在 → 管辖，除非在三级名单里被显式关掉；
- **彻底关闭某应用 = 保留条目 + `enabled=false`**（绝不能删条目——删了就落回「名单里没有=默认参与」，等于没关）。

### 4.4 数据结构与三级

| 层 | 数据类 | 字段 |
|---|---|---|
| 全局 | `RelockData` | 三个链路开关（解锁后/退出后/锁屏后）+ 三个全局延迟 + `lastOnScenes`（总开关快照）+ schema |
| 应用 | `RelockApp` | `delaySec / exitDelaySec / screenOffDelaySec`（`FOLLOW_GLOBAL=-1`）+ `enabled` + 三个逐链路开关 |
| 界面 | `RelockActivity` | 三个延迟（`FOLLOW_APP=-2`）+ `enabled` + 三个逐场景开关 |

- 哨兵：应用级 `FOLLOW_GLOBAL = -1`，界面级 `FOLLOW_APP = -2`；
- 数据迁移：`schema 0→1`（退出/锁屏从合并开关拆成两条链路，老数据继承）、`1→2`（修复全局退出延迟继承）、`2→3`（三个全局延迟回归设计文档默认值，只迁移仍停在旧默认 0 秒的项），当前 `CURRENT_SCHEMA=3`；
- 哨兵只影响**值**（延迟）的解析；「参与与否」由各层的开关决定，两者分开。

### 4.5 裁决铁律（实际实现）★

一条链路的最终结果 = **一层总闸 + 一层优先**：

1. **全局总闸**：该场景的全局开关关 → 对**所有**应用与界面一律**不锁**（一关全停）；
2. **最细的「已登记」层单独决定这条链路参不参与**：
   - 界面级已登记 → 只看它的 `enabled` 和**该场景自己的开关**，**不再看应用级**（细层覆盖粗层，绝不做各级合取）；
   - 界面级未登记 → 看应用级（`enabled` + 该场景开关）；
   - 两层都没登记 → 默认参与。
3. **等多久 = 覆盖式解析**：界面值 → 应用值 → 全局值（`FOLLOW` 哨兵逐级下探）。

**决策表（实际行为）**：

| # | 全局开关 | 界面级 | 应用级 | 结果 |
|---|---|---|---|---|
| 1 | 关 | — | — | **不锁**（总闸） |
| 2 | 开 | 已登记 · 界面总闸关 | — | **不锁** |
| 3 | 开 | 已登记 · 该场景开关关 | — | **不锁** |
| 4 | 开 | 已登记 · 该场景参与 | 任意（**包括应用级关**） | **锁**；延迟 = 界面值→应用值→全局值 |
| 5 | 开 | 未登记 | 已登记 · 应用总闸关 | **不锁** |
| 6 | 开 | 未登记 | 已登记 · 该场景开关关 | **不锁** |
| 7 | 开 | 未登记 | 已登记 · 该场景参与 | **锁**；延迟 = 应用值→全局值 |
| 8 | 开 | 未登记 | 未登记 | **锁**；延迟 = 全局值 |

> 第 4 行是「**单个界面 > 单个应用**」的落点：用户在界面层显式打开某场景后，应用层即使关掉，该界面仍按自己的设置参与（v1.24.4 按用户要求恢复界面级逐场景开关并真机验证）。
>
> 为了不出现「upsert 瞬间静默提权」，**新建界面级条目时三开关必须镜像应用级的原始值**（`newActivityMirroringApp`），保证登记前后对外零差异。

### 4.6 执行保证（不锁错人、不重复锁）

| 保证 | 实现 |
|---|---|
| 到点二次校验 | 重锁前重新查：该链路是否仍被管辖（`isTracked`，关掉开关的待锁项直接丢弃）；`pkg == 当前前台` 则跳过（**用户正在用就不锁回**）；锁屏链路要求仍在熄屏态。★ v1.24.10 起**三条链路齐全** —— 退出链路原先漏了这道，「关了开关还会被锁回去」 |
| 去重节流 | 同一目标 3 秒内只执行一次（快速亮灭屏连发 `SCREEN_OFF` 不会连环锁） |
| 计时表而非定时器 | 全部用 `HashMap/pendingRelock` + 每秒 tick 对账，不 `postDelayed`、不堆任务 |
| 线程纪律 | 前台查询与上锁动作全在后台单线程 executor；广播处理 `runBlocking` 不落主线程（防 ANR） |
| 省电 | 服务 `active() =（任一开关开）&&（收藏夹有受管辖条目）`；不满足则清表、不查询 |
| 前台保护 | 目标应用在前台时**不允许**对它上锁（防止把自己锁死 / 锁正在用的界面，与 §15.4 一致）。★ v1.24.10：「当前前台」改为**当场查询**，不再复用另一条链路顺带维护的缓存值 |

### 4.7 配置面（UI）

- **页面顶部总开关**（「自动锁闭」卡）：三条链路的聚合视图。
  - 关 = 三条一起关，并把当前组合存进 `lastOnScenes`；
  - 开 = **原样恢复**上次的组合（不是粗暴三条全开——避免把用户特意关掉的链路静默打开）；
  - 关总开关时清空待锁表（否则刚解锁的界面到点还会锁回）。
- **三条全局场景行**（解锁后 / 退出后 / 锁屏后）：场景名 → 值（顶层的值**永远是具体值**，没有「跟随上级」）→ 开关。点值弹**全 App 共用的值选择弹层**；点开关直接锁/不锁（关闭需验证）。
- **解锁验证卡**：显示锁回后靠什么解锁（跳「解锁验证」页）。
- **管辖范围**（按应用分组）：
  - 应用行 = 图标 + 名称 + 状态（`已启用 N / M`、`已暂停（总开关已关）`、`已关闭 · N/M 单独开启`）+ **应用总开关** + 「已解锁 N」；
  - 应用级三条场景行（值灰=跟随全局 / 蓝=自定义；**开关亮着就一定真的会锁**）+ 「解锁条件」入口 + 「最严执行」提示；
  - 每个应用的界面列表**默认收起**，展开后每个界面三条场景行（各带开关）+ 解锁条件；
  - 页脚：`全部开启` / `全部关闭`（关闭需验证）；`添加应用级规则`；`紧急操作 → 立即重新锁全部`。
- **宫格应用弹窗**（工作台点应用图标）：界面列表**在上**（每行 = 名称 + 锁定开关，默认折叠），自动锁闭三条场景行**在下**（默认折叠，折叠头显示 `N/3 参与`）。
- **值选择弹层（全 App 共用，固定两项）**：`跟随上级`（附注显示上级当前生效值）/ `自定义时间`；自定义区 = 数字框 + `[秒｜分钟｜小时]` 分段 + 等效时长回显（`等待 5 分钟` 这类人话）。**不提供「不锁」入口**——不锁只由开关表达。
- **点值自动开开关**：开关为关时点值 → 先自动打开该场景开关，再弹层（否则「改了个寂寞」）。
- **反向操作**：调大延迟 = 削弱 → 需验证；调小 / 开关打开 → 直接生效。

### 4.8 与收藏夹锁定状态的关系（v1.23.6 引入，**v1.24.16 修正**）

- 收藏页（列表行 / 宫格弹窗 / 详情）**锁定某个界面** → 把该界面**纳入自动锁闭**
  （v1.24.16 起改为只开该界面的总闸 `setActivityMasterOn(true)`：已登记条目**逐场景配置不动**，
  未登记条目走 `newActivityMirroringApp` **镜像应用级当前值**）；
- **解锁某个界面 → 不再改动自动锁闭**（v1.24.16 修正）。
  ★ v1.23.6~v1.24.15 期间这里是「解锁即退出自动锁闭」（`setActivityAllLinks(false)`），
  真机事故 2026-10-14 证明它有害：用户为了**试验自动锁闭**而先解锁微博，
  这一动作把 `MainTabActivity` 从自动锁闭里静默摘除，而界面级压过应用级（v1.24.4）——
  于是「锁屏后自动锁回」**永远不可能发生**，应用级开关却还亮着 = 假开关。
  **「当前锁没锁」与「要不要参与自动锁闭」是两件事**：自动锁闭是一套策略，
  它的全部意义就是「解锁之后还会自己锁回来」；想「临时用一会儿不被锁回」请走**临时解锁**（限时豁免）。
- ★ **界面级「总闸」显示值 = 三层裁决结果**（`enabledByState`：三条链路任一生效即为开），
  与详情页三个开关**必然一致**——它们读的是同一个函数（关总闸 = 三场景全关；开任一场景 =
  总闸自动打开，且**只开这一条**，不动另外两条）。v1.24.12 起所有开关显示值都取裁决结果，
  「已配置但被上层暂停」由文字提示承担，不再用亮着的开关表达。
- ★★ **「更细层压过更粗层」必须处处可见**（v1.24.16）：应用级开着、而它下面**有界面被单独关掉**时，
  ① 设置页折叠标题写 `各界面单独设置（N 个，M 个已关闭）` 并转**警示色**；
  ② **工作台宫格弹窗的「自动锁闭」卡下方也加同款红字警示**
  （`M 个界面被单独关闭，实际以界面级为准`）。真机事故里用户看的是**宫格弹窗**，
  而当时只有设置页有警示 → 他盯着一个「开着的开关」找不到原因。

### 4.9 磁贴与计数口径

| 磁贴/计数 | 口径 |
|---|---|
| 「全部锁闭」磁贴（雪花） | 单击 = `relockAllPending()` + `relockAllListed(respectScope=false)` ——**忽略**「是否参与自动锁闭」开关（紧急动作语义：「现在都锁上」）；长按 = 打开主页 |
| 磁贴副标题 | `待锁 N 个` / `可锁 N 个`（`countUnlockedListed()`，不受参与开关限制）/ `均已锁闭` / `收藏夹为空`——口径与单击动作严格一致 |
| 页面「参与 N 个」 | 收藏夹里受管辖的条目数（三层裁决后 `lockSec >= 0`） |
| 服务通知 | `守护 N 个目标，待锁 M 个` |

## 5. 四功能的交叉关系

### 5.1 拦截判定优先级（Watcher 实际顺序）

```
启动请求 →
  ① 全局豁免（临时解锁中）        → 放行一切
  ② 到点跳转闸（连续使用到点/已收走）→ 拦截 + 送目标
  ③ 包级拦截（超额 / 专注中）      → 拒绝（超额带额度页）
  ④ 组件规则（收藏锁定的界面）     → 拒绝（可带跳转；到期的自动放行）
  ⑤ 都没命中                     → 放行
```

### 5.2 叠加矩阵（谁会盖过谁）

| 组合 | 实际结果 |
|---|---|
| 临时解锁 × 其它一切 | 豁免期内全部放行（优先于所有拦截）；**不改变**锁定/冻结状态，到期恢复原拦截 |
| 自动冻结 × 跳转 | **互斥、跳转优先**：已配跳转的包不冻结；已冻的包配了跳转会被自愈解冻 |
| 自动冻结 × 自动锁闭 | 二者可同配但语义重叠：冻结 = 图标消失（更狠）；锁闭 = 图标在但点不进。同一应用只想要一种效果时，跳转场景选锁闭、彻底戒断选冻结 |
| 自动锁闭 × 时长限额 | 限额超额后 Watcher 包级拦截优先（额度页）；自动锁闭仍会照常把解锁过的界面锁回（状态层），二者叠加 = 更紧 |
| 自动锁闭 × 专注会话 | 专注中目标包整包静默拦截（比界面级更紧） |
| 解锁验证 × 全部 | 所有「解锁/削弱」动作的前置门槛；自动锁闭的「回锁」是加强动作，不受它阻塞 |
| 定时计划 × 临时解锁 | 开「计划窗口内禁用」后，计划生效期间豁免不激活——同一判据四处共用（writeRules 不下发 `g` 条目 + 验证页进门拦 + 磁贴点击拦/置灰） |

### 5.3 典型走查

**A. 锁抖音、从搜索页刷 15 分钟**
1. 收藏夹锁定 `SplashActivity`（跳转 `snssdk1128://search?keyword=`）→ 入口锁上、点图标直达搜索页；
2. 用户玩完退出 → 「退出后」链路记时（如设 0 秒）→ 1 秒内重新上锁；
3. 若中途临时解锁过：豁免期内放行一切；到期重新拦截。

**B. 想彻底戒断某 App（连搜索页也不给）**
- 加进自动冻结名单，开「锁屏后冻结」+「退出后延迟冻结」→ 锁屏/离开一会儿后整包消失；
- 该应用若配了跳转会被自动跳过冻结（跳转优先），此时应改用自动锁闭把入口锁死。

**C. 微信只锁朋友圈，其它正常**
- 收藏夹只锁 `SnsTimeLineUI`；「解锁后/退出后/锁屏后」可分别开关；
- 微信整体不想被自动锁闭 → 应用级三开关全关；但朋友圈界面级保持打开 → **单个界面 > 单个应用**，朋友圈仍会回锁。

### 6.3 八轮核对发现并修复的缺陷（均已修复）

本轮「以实际功能为准」逐模块读代码时，抓到两处**界面有、实际不生效**的缺陷——都属于本 App 最忌讳的「假开关 / 静默改写」，已在同一次构建内修复，故上表按**修复后**的实际行为填写：

| # | 缺陷 | 影响 | 修复方式 |
|---|---|---|---|
| 1 | **每日临时解锁次数上限完全没接线**：`tempUnlockAllowed` / `recordTempUnlock` / `tempUnlockUsedToday` 三个函数在全工程**零调用点**，设置页把上限写进 prefs 却没人读；验证页通过后直接发豁免 | 用户选「每天 1 次」照样能解锁无数次，磁贴永远可点 = 假开关。另外原计数按**包**存 JSON，而临时解锁是**全局**动作（一次放行所有锁定界面），按包计数根本没有对应的操作语义 | 改为**全局**单计数器（`tu_used_today` + `tu_date`，跨日归零）；三处接线：① 设置页常驻显示「今日已用 N / M 次」；② 磁贴同判据（`临时解锁已禁用` / `今日次数已用完` → `STATE_UNAVAILABLE` 置灰）；③ 验证页进门先过闸，不过闸则不进验证流程、只给「返回」 |

#### 第六轮（v1.24.13 / v1.24.14，用户报「应用层级的自动锁闭开关没有效果」）

起因：v1.24.12 装机后用户报「刚才测试发现应用层级的自动锁闭开关没有效果」。真机截图：收藏页微博
弹窗里应用级「锁屏后」亮着、副标题「1/3 参与」，但息屏后一条都不锁。

**真机取证**：进「设置 → 自动锁闭」展开微博卡片的「各界面单独设置（1 个）」，
界面级 `MainTabActivity` 的**三个场景开关全是关的**，而应用级「锁屏后」是开的 —— 副标题写作
「已启用 0 / 1」。两条证据链指向同一个结论。

**根因（结构性，两个方向都断）**：

1. `newActivityMirroringApp()` 在界面条目**创建那一刻**把应用级三条链路的原始值**一次性快照**进去；
2. 之后用户在应用级再拨动开关，界面级条目**不会跟着变**（只读覆盖，没有任何回写）；
3. 而 `resolveLockSec()` / `lockSecByState()` 对「已登记」界面是 `return`，**根本不看应用级**
   （v1.24.4 为满足「单个界面优先于整个应用」刻意如此）。

→ 结论：**只要一个应用下有任何一个界面级条目，它的应用级三个场景开关就 100% 失效**。
应用级开也白开、关也白关（关的方向还额外多一层：`app.enabled` 同样不参与界面级裁决）。
`RelockApp` 的数据类注释写着「这是应用总开关之外的**逐链路闸门**：界面级无法越过它生效」——
**代码与自身规格直接矛盾**，这正是 v1.23.5「反合取」改过头留下的旧账。

#### 第七轮（v1.24.15，v1.24.14 装机后自愈**无效**，追查到的第二层根因）

起因：v1.24.14/78 装机后进「设置 → 自动锁闭」复查，微博卡片**依旧**是
「已启用 0 / 1」，展开 `MainTabActivity` 整行是关的 —— 自愈没生效。

**真机取证（逐层排除）**：

1. logcat 无 `healLinkDrift` 输出 → 自愈判据把它跳过了（不是没编译进去，也不是没跑）；
2. 展开微博卡片确认形态：界面级**整行 `enabled = false`**、应用级「锁屏后」开着、
   应用行总开关也开着。

**根因（v1.24.13 判据的第二层漏洞）**：v1.24.13 的自愈判据是「界面**三条链路全关** ∩ 应用有链路开着」，
而微博那条是**「整行 `enabled = false`，但三条链路字段仍是 `true`」**的**混合状态**：
首句 `if (!a.enabled) return` 先跳过一次，后面的条件也都不成立 → 两条路都漏掉。

这个混合状态是**写出来的**：`setActivityEnabled(..., false)` 与 `setActivityMasterOn(..., false)`
（界面行总开关、「收藏页解锁」等入口都走它们）**只翻 `enabled`，不碰三条链路** ——
与 v1.24.13 修掉的 `setAppParticipating(false)` 是**同一类缺陷**（关闭只打标记、不真的停），
只是当时只扫了应用级、没扫界面级。

| # | 缺陷 | 影响 | 修复方式 |
|---|---|---|---|
| 27 | ★★ **界面级「关闭」只置 `enabled=false`，三条链路保留 `true`**（`setActivityEnabled` / `setActivityMasterOn`） | ① 「关掉了什么」在界面上不可见；② 该混合状态**骗过自愈判据** → 应用级开关对它永久失效（本轮用户报的「没修好」） | 两个方法关闭方向都改为**三条链路一并置 false**（口径同 `setAppParticipating`）；打开方向不变（仍只翻总闸，避免把用户刻意关掉的场景一起打开 —— 这一点 [缺陷 22] 的教训） |

> 只把「开」写穿不够 —— 关闭若只翻一个布尔、把场景字段留着 `true`，
> 就同时制造了「不可见」和「判据失效」两个问题（缺陷 27）。
> 判据：**任一「关闭」入口执行后，该层及其下层的链路字段应全为 `false`**；
> 目录里若还存在「整行关着、链路全 `true`」的条目，那一定是老数据或还有没扫到的入口。

#### 第八轮（v1.24.16，v1.24.15 装机后用户报「微博的自动锁闭**还是没有**效果」）

起因：v1.24.15/79 装机后用户**再次**报同一现象 —— 并直接质问「你刚才修了没有？」

**先诚实回答这一问**：上一轮**确实修了**（`syncAppLinksDown` 写穿 + `healLinkDrift` 自愈 + `setAllEnabled` 收紧），
也曾在本机验证通过。但用户这次的「没效果」是**另一条链路**把界面级**重新破坏**掉了 ——
两件事**同源**（都是「界面级压过应用级」），但触发入口不同，所以上一轮的自愈只修好了**存量**，
没堵住**新产生**脏数据的那个入口。本版一并收口。

**真机取证（这一次特意从「用户是**怎么操作**的」这个角度重新走了一遍）**：

1. 工作台显示「已锁定 7 个界面」+ 微博卡片「🔓 未锁」（与用户截图完全一致）；
2. 微博弹窗「自动锁闭 1/3 参与」→ 自动锁闭页微博卡片「已启用 0 / 1」+「各界面单独设置（**1 个，1 个已关闭**）」；
3. 展开界面列表：`MainTabActivity` 行开关 `checked=false`、三条场景字段**全 false**（**不是**上一轮那种「整行关、链路仍 true」的混合态，所以自愈判据不认为它需要被救 —— 它是用户**刚刚才制造出来的**）；
4. 实测复现：`input keyevent 223`（息屏）→ 亮屏 → 微博**依旧未锁**。

**根因（第三层，且是「刚产生」而非「存量」）**：

`FavoritesScreen.kt` 的「**解锁这个界面**」动作里藏着 `AutoRelock.setActivityAllLinks(pkg, cls, false)`
（v1.23.6 引入）—— **一次「解锁」顺带把该界面从自动锁闭里整个摘除**。

用户为了**试验**自动锁闭，第一步当然是「先解锁看看」，于是：

> 应用级开「锁屏后」→ 用户点「解锁微博」→ 界面级被静默关掉 → 界面级压过应用级（v1.24.4）
> → **锁屏后永远不可能回锁**，而应用级开关还亮着 = **假开关**，且**每次试验都会复现**。

所以上一轮的自愈「治好了存量、治不了复发」：只要用户再点一次解锁，脏数据立刻回来。

| # | 缺陷 | 影响 | 修复方式 |
|---|---|---|---|
| 31 | ★★ **「解锁界面」= 静默摘除自动锁闭**（`FavoritesScreen` 的解锁分支调 `setActivityAllLinks(..., false)`，v1.23.6 引入） | **语义混淆 + 假开关**：「当前这把锁没锁」和「这个界面要不要参与自动锁闭」是两件事，被写成了一个动作。用户每试验一次就破坏一次，应用级开关立刻变假 | 删掉 `FavoritesScreen` **两处**（列表行 `ruleToggle` 与验证通过后的 `pendingUnlock.onConfirmed`）的 `setActivityAllLinks(..., false)`。语义修正为：**解锁只管解锁**；想「临时用一会儿不被锁回」请走**临时解锁**（限时豁免），那才是它该管的事 |
| 32 | **「锁定界面」= 顺带打开三个场景**（锁定分支调 `setActivityAllLinks(..., true)`） | 用户只在应用级开了「锁屏后」，在收藏页锁一下界面，却被**顺带打开**「解锁后 / 退出后」 —— 静默加宽用户的配置（与 [缺陷 22] 同一类） | 改用新增的 `AutoRelock.setActivityMasterOn(pkg, cls, true)`：**只翻该界面的总闸**；条目未登记时走 `newActivityMirroringApp()` **镜像应用级当前值**，不会凭空全开 |
| 33 | **自愈判据仍写死 `1` 版，救不了「用户刚制造」的条目** | 装机后再次验证仍是「没修好」的观感 | 判据不变（仍是「整行关着 ∩ 应用仍在管辖内」），把 `LINK_DRIFT_HEAL_VER` 2 → **3** 重跑一次，用于复原**已经被 v1.23.6 旧耦合摘除过的存量条目**（如微博） |
| 34 | **「更细层压过更粗层」只在设置页折叠标题可见**（工作台宫格弹窗完全无声） | 用户当时看的正是**工作台那张卡**，看到「1/3 参与」却找不到原因 | 宫格弹窗的应用级「自动锁闭」卡上补**红字**：「N 个界面被单独关闭，实际以界面级为准」（判据 `!activityEnabledByState(pkg, cls)`，只在应用本身有场景生效时显示，不误报） |

> 若有，就是在制造假开关，且**用户每操作一次就复发一次**（自愈救不了）。
